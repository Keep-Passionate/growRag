# S2G 第一课：先知道系统实际做了什么

中心思想：改进一个系统之前，先确认哪个步骤真正影响输出。看到一段不准确的解释，不足以证明它导致错误；要追到实际执行的查询和检索结果。

## 一个真实例子

材料固定选自旧开发白名单第 1 题，未按成绩挑选：
`5add20435542990d50227df5`。原问题：

> Force India VJM01 was the only car constructed by a team that was created after of buyout of what team?

大意：制造这辆赛车的车队，是收购哪支车队后成立的？

| 时刻 | 记录告诉我们的事实 |
| --- | --- |
| 第一次 Judge 前 | 可见证据为空 |
| Judge 输出 | 一个 gap 查造车的车队名称；另一个 gap 查收购关系 |
| 实际查询 | 完整原问题，再追加 `Force India VJM01 team team_name` |
| 实际检索 | 有序返回 6 篇文档；首篇为 Spyker F8-VII，第三篇为 Spyker F1 |
| 选句 | 第一篇第 1、4、6 句，第三篇第 1 句 |
| 下一次 Judge | 只看到累计的这些选句组成的证据，不是全部检索段落 |

不展示最终答案或正确标签。本课没有判断答案对错。

这个例子保留了原问题中的 buyout（收购）关系。因此不能说“查询没有使用第二个关系 gap，所以关系消失了”。此外，查询只用第一个 gap，而选句提示最多使用三个 gap；一个字段可能不影响搜索，却影响后面的选句。需要逐个模块核对。

请先用自己的话回答：**我们直接观察到了什么？哪一步还不能推出因果结论？如果要检验关系修正，你会怎样避免同时改变其他因素？**

## 论文、作者代码、Qwen 迁移分别是什么

| 检查项 | 作者固定代码 | 本项目旧 500 开发批次 |
| --- | --- | --- |
| Judge，即证据充分性判断器 | 基础模型加载训练后的 LoRA 适配器 | 固定 Qwen API，无作者训练 Judge |
| Judge 输入 | 原问题＋此前累计选句；初始为空 | 保留此控制顺序 |
| gap 到 query | 原问题加 gap 的 target/slot；缺失时回退 description | `paper_k1`，查询只用第一个 gap |
| 选句提示 | 原问题、最多三个 gap 提示、编号句子 | 沿用提示与指针规则，模型替换为 Qwen |
| 检索 | Lucene，先取 50，排除已检索文档，再保留 6 | SQLite BM25，共享 72713 段封闭语料，查询词去重 |
| 停止 | 充分或到轮数上限；初始空证据须至少检索一次 | 最多 4 次检索；上限仍强制回答 |
| 额外停止规则 | 这里未发现边际增益、重复 query 或停滞停止 | 没有增加这些规则 |

LoRA 是训练出来的一组较小参数，接在基础模型上改变它的判断行为。把提示词交给另一个未做该训练的 Qwen，不等于使用相同 Judge。

作者 README 说明使用 Llama3.2-3B Judge 和 Llama3-8B reasoner；训练脚本及加载路径能证明这里存在训练。**本轮没有重新逐段核对论文 PDF 的全部实验设定、训练数据和报告数字**，因此不声称已经复核论文原版成绩。后续精读应把论文主张、代码实现和本地迁移逐项对照。

旧批次最多 5 次 Judge、4 次选句、1 次回答，共 10 次模型调用。4 轮是检索预算，不是只调用模型 4 次。到上限回答也不等于证据已经充分。

## 这轮数据究竟证明了什么

固定原顺序前 10 题，零 API 重放 18 次检索。实际 query、检索结果顺序与内容、选句指针及 28 次判决前证据均一致。这证明我们能还原这一小批原臂的执行；模型输出使用旧记录，没有重新生成。

构造的“只改 description”检查也保持 query 与选句提示不变，前提是 target/slot 完整。这是代码行为检查，不是答案效果实验。

还不能证明：关系修正有益、删除 gap 更差、Judge 判断正确、历史记忆有用、方法有创新。原方法通常保留完整原问题，所以“关系缺失”本身也需要先找到具体、可观察的依据。

## 下一步为什么先讨论，而不是立刻加模块

我们先一起定义：怎样才算实际查询没有清楚表达关系？排除原 query 已明确表达关系的题，再讨论修改的具体规则。否则容易把“我们喜欢的改写”当成“系统缺失的能力”。

待共同确定的三个候选对照是原样、删除可疑 gap、修正关系。比较时保持原问题、初始证据、索引、结果数、轮数与评判方式一致；修正不能使用未来证据或答案。先看检索/选句差异，确有值得检验的现象后再核实 API 预算，评价最终答案。

如果没有足够案例支持问题存在，修改或放弃假设是正常的科研结果。本轮先学会这一步，而不扩大经验库或训练路由。
