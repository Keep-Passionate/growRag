## 2. 三条路线不是三层记忆

BASE、FRESH、REUSE 是动作来源，不是记忆层数：

```text
原问题 q0
  ├─ BASE  ：不改写 ──────────────────→ RAG
  ├─ FRESH ：当前题单独生成 query ────→ RAG
  └─ REUSE ：历史动作指导生成 query ──→ RAG

检索可使用改写 query；回答者始终回答原问题 q0。
```

每条分支的 RAG 在本批都很简单：在该题的候选上下文内做句级 BM25 检索，取前 4 个句子，再让同一固定 Qwen 回答。不是全维基检索，不是完整 Hotpot 榜单系统。

记忆的两种时间范围则是：

- **本题局部记录**：当前题已经检索到什么、试过什么、还缺什么；不自动影响以后问题。后续多轮时使用。
- **跨题长期经验**：经过筛选的历史查询操作，供其他问题选择复用。原始轨迹另外保留审计，不把历史答案直接给新题回答者。

DocumentSession 文档层继续后置。本题内的执行记录和长期卡可以保留为两个层次，但不能因为文件里已有相应类，就称完整双层 Agent 系统已运行。

FRESH 的含义是“不使用跨题历史”，**不必然意味着多轮，也不必然意味着检索后**。未来它可以读取本题先前证据和失败尝试，仍然算 FRESH。它既是新情况的处理路径，也是检测历史究竟有没有额外价值的对照；不是专门用于抵消历史漂移的补丁。

## 3. 当前 FRESH 到底怎样改写

关键入口：[query_actions.py](D:/project/GrowRAG/src/growrag/query_actions.py:82)、[pre_pilot.py](D:/project/GrowRAG/src/growrag/experiments/pre_pilot.py:146)、[query_comparison.py](D:/project/GrowRAG/src/growrag/experiments/query_comparison.py:219)。

当前批次固定 `PARAPHRASE`，也就是措辞改写；不是自动从扩写、分解、改写中挑动作。实际模型为 `qwen3.7-flash-2026-07-15`，temperature=0、关闭 thinking，输出上限 768 tokens。

提示词的意思是：

> 为原问题生成一条搜索查询；保持原意和实体、关系方向、时间及否定条件；可以调整词汇，不需要先证明有结构缺口；不要编造事实；允许原样返回；只输出 query JSON。

输入约为：

```json
{
  "original_question": "当前原问题",
  "form": "paraphrase",
  "intent": "保持问题目标，调整搜索用词",
  "current_evidence": [],
  "previous_queries": []
}
```

这只是对真实英文提示词的中文解释，不是可复现实验所用的新 prompt。真实版本名是 `growrag-paired-query-v1`，原文以代码和 API 审计为准。

流程是“改写一次 → 本地检索 → 生成答案”。它没有先读取 BASE 的检索结果，没有 S2G 式 gap，没有检索排序反馈训练，也没有训练小改写模型。代码会检查 JSON 格式、长度、非空等，但**语义保真主要靠提示词，尚无自动证明**。

因此应称“GrowRAG 的冻结提示词单步 FRESH 对照”，不能称完整复现 ReFormeR、RaFe、ReflectiveRAG 或 S2G。前人更强的方法应另设基线，不能把这个简单 FRESH 当作领域最强无记忆方案。[Query Rewriting / EMNLP 2023](https://aclanthology.org/2023.emnlp-main.322/)、[RaFe / Findings EMNLP 2024](https://aclanthology.org/2024.findings-emnlp.49/)是增强无记忆改写需要核对的方法来源。

## 4. 为什么 FRESH 还不如 BASE

本批 64 来源的结果：

| 指标 | BASE | FRESH |
|---|---:|---:|
| 答案 EM | 36/64，56.25% | 34/64，53.125% |
| 平均答案 F1 | 0.60625 | 0.5828125 |

FRESH 把 3 道原本没答对的题改对，同时把 5 道 BASE 答对的题改坏。不能由 64 道来源题推断“改写普遍无用”，更不能据此证明历史记忆有效。

原因要分开排查：词义大致不变仍可能改变 BM25 排序；压缩会丢检索线索；top-4 句子预算可能把需要的两条证据挤掉；Reader 缺证据会弃答；答案表达不同也可能导致 EM 下降。同样查询下的生成波动不能归为改写功劳。

当前底座很小，这正适合找错误，不适合宣称强方法优劣。下一步应保留这个冻结对照，再在调试集上确定一个更强、同预算的无历史改写版本，单独编号；不能看封闭检查集后反复改 prompt。

## 5. 0→1、0.5→1、EM、F1

- **EM = Exact Match，完全匹配。** Hotpot 的答案文本经规范化后相同得 1，否则得 0。单题 EM 0→1 表示从未匹配标准答案到匹配，不是置信度从 0 到 1。
- **F1-score，也称 F-measure 的 β=1 形式。** Hotpot 答案 F1 衡量预测答案和标准答案词语的重合，综合 Precision（预测词中有多少正确）与 Recall（标准词中找回多少）：`F1 = 2PR/(P+R)`。这里不是分类任务的宏平均 F1。
- **支持句 Recall@4**：检索前 4 句命中了多少比例的人工标注支持句。两条标注句找到一条是 0.5，找到两条是 1。这不等于答案置信度，也不是逻辑充分性的证明。

例如 gold 是 Sacramento，输出 Sacramento, California，词级 P=1/2、R=1，F1≈0.667，但 EM=0。这个例子提醒我们：EM 不匹配不自动等于事实错误。

官方还有 supporting-fact 及 joint 指标。当前简化的“答案 EM/F1＋检索支持召回”不能冒充完整官方评分。标注以外也可能存在有效证据，而命中标注句也不保证 Reader 正确理解。[Hotpot 官方评分脚本](https://github.com/hotpotqa/hotpot/blob/master/hotpot_evaluate_v1.py)

## 7. 历史具体保存什么；M1–M5 是什么

不是只存一段摘要，也不是把所有上下文塞进下一次回答。当前分用途保存：

| 用途 | 内容 | 为什么保存 |
|---|---|---|
| 原始来源记录 | 原问题、实际改写、独立 BASE/FRESH 的检索与答案、事后反馈、模型/prompt/索引配置 | 能查清卡片如何产生；不能只相信摘要自述 |
| 经验卡 | 适用阶段/问题模式、前提/禁用条件、动作正文、保留约束、来源、版本、验证和使用统计 | 提供可选择、可追踪的查询操作 |
| 选择视图 | 同一来源的 M1/M2/M3/M5 表达 | 实验“选择器看什么信息更容易选对” |

卡片主要结构对应 [cards.py](D:/project/GrowRAG/src/growrag/experience/cards.py:340)：

```text
card_id / version / lifecycle_state
activation : stage / query_pattern / preconditions / contraindications
repair     : operator_type / intent / action_body.{rewrite_rule, preserve}
provenance : source_refs[*].{source_id, source_fingerprint, admission}
             extraction_prompt_version
validation : matched_trials / benefit_count / neutral_count / harm_count
             verification_tier
serving    : use_count / last_used_at / expected_cost
parent_versioned_ids
```

当前 6 张卡都是 candidate；`matched_trials=0`。来源所含几个文档，不等于在几个独立新问题上成功。初始化的 0 计数也不是经校准的“置信度=0”。源码中的晋升阈值是工程策略参数，不是已被论文实验支持的安全界限。

M 编号是**表示方式**，不是五个 memory 层，也不是五种改写动作：

| 表示 | 给选择器看的内容 | 当前安排 |
|---|---|---|
| M1 具体改写对 | 过去的 q 和实际 q′ | 首轮 |
| M2 通用经验摘要 | 简短自然语言说明怎样改 | 首轮 |
| M3 参数化动作 | 对象/属性槽位、操作和需保留信息 | 首轮 |
| M4 状态—动作 | 当前/历史缺口、动作、预期补充 | 留给检索后研究 |
| M5 条件—动作—核查 | 做什么、什么条件适用、哪些未知或需检查 | 首轮 |

首轮固定同一候选集合、选择器、当前问题与规范动作。M1/M2/M3/M5 **只改变选择器看到的视图**；同一 ID 一旦选中，执行器都只得到相同动作正文。否则无法知道变好是“更会选”还是“执行器拿到更多提示”。

M2/M3/M5 当前只是接受外部明确提供的文本，不是已经自动生成并验证完成。1200 字符上限也不等于固定 token 数。

FRESH 不读这些历史视图；它仍可有当前题的结构化输入。使用 JSON 或 gap 结构不自动等于用了长期记忆。

## 8. “软条件提示：未知标记留给选择器权衡”

更清楚的说法是：**把已确认、已冲突、尚未知区分开；未知不冒充成立，也不一律当失败。**

教学例子：一条动作擅长把双对象的时间比较转成两个时间线索。新问题明确比较两部影片上映先后，“双对象、时间比较”可从问题中看见；“语料是否用 released 这个词表达”在尚未检索时未知。未知是风险提示，不代表已经验证，也不必然要求拒绝整个候选。

有三条边界：

1. 已经明确改变原问题意图、关系方向、否定条件的冲突，不能以“软”之名放行。
2. 对决定动作合法性必不可少的条件，未确认时应补查或放弃该动作，不能靠模型猜。
3. 如果条件本身要求提前知道答案，例如“只有这两个城市实际位于同一国家才使用”，这是不合格的 PRE 条件，应审查卡片定义，不能把未知的答案交给选择器瞎猜。

目前还没有完整的逐条件三值验证器。已有提示词提醒不要假设条件成立；下一步希望显式记录条件状态及其可观察依据，再比较硬拒绝、软提示和不提供条件的差别。先在调试集设计，不把模型自报分数当概率校准。

## 9. 选择器在哪里；QPP 三选一可不可以

### 当前表示实验的选择器

```text
当前问题
  → 按来源问题词面重合召回同一批候选（最多 3 条）
  → M1/M2/M3/M5 分别让同一选择器选“卡 ID 或 FRESH”
  → 先把全部选择落盘
  → 离线执行 BASE、FRESH、每张卡对应的规范动作，各一次
  → 事后评分，评估哪种表示更会选择
```

词面召回使用 Jaccard，不是可信性评分，也不是 QPP；文档检索才使用 BM25。当前选择器在**历史改写生成之前选卡**。BASE 是这个实验的独立对照，不在 selector 可选标签内；拒绝统一回 FRESH，是为了隔离表示效果，不是整个产品永远不能回 BASE。

离线把各候选都执行，是为了知道选对没有。部署不能先免费知道谁最好；把所有分支跑完按 gold 选最好叫 oracle 事后上限，不是可以拿来上线的路由。

### 用户提出的下一阶段候选查询选择

```text
                         ┌─ BASE 原 query
当前问题 + 历史候选 ──────┼─ FRESH 现场生成 query
                         └─ 各历史动作分别生成 query（先最多 3 条）
                                     ↓
                           去重、约束检查、QPP 预测
                                     ↓
                             只选一条进入完整 RAG
                                     ↓
                       后续再研究：证据不足时有限修复
```

这个设计可行，但“多候选＋QPP 选一”已有直接工作。QPP 是 Query Performance Prediction，查询表现预测；预测目标可能是检索质量，而不是答案正确率。Pre-retrieval QPP 在候选文档检索前预测，Post-retrieval QPP 则已经支付候选检索成本。已有 QPP 论文明确区分候选生成和完整 RAG 的成本。[QPP Query Variant Selection](https://arxiv.org/html/2604.22661v1)

建议先做当前表示实验，再比较这条候选查询路由，不同时更换记法、执行器、候选数与选择器。也不要无必要地叠加两个昂贵 LLM 选择器；前级可以只是便宜的短名单。

**新增必要对照**：若允许 BASE/FRESH/REUSE 中选择，应比较：

- 无历史策略：从 BASE＋FRESH 中选。
- 有历史策略：从同一个 BASE＋FRESH＋历史候选中选。

否则收益可能只是“避开了差 FRESH、退回 BASE”，并非历史内容有效。另加等候选数的无历史多改写/静态动作模板对照，排除多给了几次尝试本身的收益；所有候选生成费都计入。

## 10. 未来 gap 与停止条件，不与当前结果混淆

当前 PRE 单轮没有 gap。未来 POST 可以沿 S2G 的问题：**缺哪一个实体、属性、关系或证据跨度？** 把下一动作写成补证据的查询，而不是让模型无目的地再说一遍。[S2G 作者代码](https://github.com/nianaaa/S2G-RAG)、[正式论文](https://aclanthology.org/2026.acl-long.1185.pdf)

建议本题状态至少包含：原问题、累计证据 ID 与内容、仍缺的项目、已执行 query、已尝试动作、剩余预算。累计证据来自实际检索结果去重，不是模型凭空写的总结。

当前 [outer_loop.py](D:/project/GrowRAG/src/growrag/outer_loop.py:200) 已有循环上限、重复 query、可选充分性信号、无增益停止接口。不过需要注意：默认 RAG 适配器的 Reader 每次只读本轮检索证据，**未自动读取外层累计证据全集**。完整闭环还需要明确组装与截断，不能仅接一个 judge 就声称已复现 S2G。

后续建议在调试集对最大 1/2/3 次 RAG 做成本—收益比较，再固定上限；不是主观选一个大数字。停止分三类：

- 证据已足够支持原问题：正常回答。
- 候选重复、证据没有可核查新增、预计继续收益低：停止搜索，但可能需要保留不确定性或弃答。
- 达到轮数/token/费用上限、调用失败：预算或异常停止，不假装答案已被支持。

“支持足够”与“继续查不值得”是两种停止理由。模型自报高置信度不能取代证据检查。停止收益思想可进一步对照 [ReflectiveRAG](https://aclanthology.org/2026.eacl-industry.27/)，此处不是声称已经实现其判据。

## 11. 如何记录落败经验，是否同题允许多卡

用户提议值得作为后续维护实验，但要把四种反馈分开：

| 观察 | 能说明什么 | 建议动作，尚未实现 |
|---|---|---|
| 词面/语义匹配高 | 问题或操作相似 | 仅进入候选，不等于有效 |
| QPP 预测落后 | 选择器预测不占优 | 记录预测，不直接减少真实成功次数 |
| 实际 REUSE 比 FRESH/BASE 更差 | 当前条件下出现负增益 | 追加真实配对事件，考虑局部降权/限用 |
| FRESH 在该状态确有新增收益 | 可能形成新操作来源 | 按准入规则产生新 candidate，不覆盖旧卡 |

不建议“高匹配但未被 QPP 选中就永久淘汰”，否则会把预测器偏见固化为记忆失效标签。一次无增益也不同于一次有害；先保留 positive / neutral / harmful / unknown 与反馈来源。

同一题可以在未来保存不同动作或不同条件下的多条经验，先做规范动作去重，避免重复增加成功计数。现有第一轮表示协议要求一题一来源候选，不允许直接塞入同题多卡；需新协议版本，不能悄悄改变已冻结实验。

老正文不原地改写：记录追加，必要时从原始轨迹生成新候选、保留来源和版本，独立比较新旧，再决定是否替换。EMA 可以平滑近期收益，但不是越老越差的证明，也不是未选中就应该遗忘的理由。反馈统计可以更新很多次；正文抽象派生深度另行限制。

冻结评价期间不能把检查题 gold 写入记忆。流式实验则先预测，再按预定权限获得反馈并更新，单独报告；保留不参与更新的探针题。

线上如果只执行 winner，就不知道落选 BASE/FRESH/REUSE 的真实答案。因此不能每题免费更新全部反事实净收益。需要离线配对数据，或明确预算的小比例审计；无配对时标记未知，不造标签。

## 12. 中间过程记录：已有与要补的内容

已有来源记录包括原问题、实际 query、每轮证据及来源、答案/引用、评分、是否准入、模型版本、prompt、请求/响应、调用次数与 token/费用。API 审计记录实际请求正文和响应，不是只有哈希；认证密钥和请求头不保存为实验输入。

新表示选择器已有选择 ID、输入指纹、状态和调用审计，但没有完整的结构化“选择依据”报告，也还没有真实目标四组轨迹。因此下一步应输出逐题易读报告，缺失阶段明写“未运行”：

1. 当前 q0、阶段、轮次及模型/prompt/索引版本。
2. 召回了哪些历史：卡 ID、来源、版本、召回方式与分数。
3. 每条卡的成立/冲突/未知条件；依据指向当前输入，不用隐含答案。
4. 实际生成的 BASE/FRESH/各卡 query；有无去重或约束拒绝。
5. QPP 若启用：预测目标、各分数、选中项、回退原因；不得标成真实效果。
6. 真正执行的查询与检索、答案、引用、停止原因。
7. 选择冻结以后，才添加离线配对评分及误用/误拒分析。
8. 哪些反馈允许写回，为什么新增/降权/保留；明确比较对象是 BASE 还是 FRESH。
9. 候选生成、选择、RAG、建库和对照各自的成本。

只要求简短可核查的理由码/证据定位，不需要保存或生成冗长 CoT。原始日志不可倒写；后来的人工解释要与当时选择器的真实输出分开标识。

## 14. 主要基线与创新边界

### 主比较建议

- 保留 BASE、当前 FRESH、加强版无历史改写，以及等候选数的无历史查询选择。
- **主要历史模式对手建议 ReFormeR**：最接近“从成功改写抽取规则，再选规则应用到新查询”。正式发表于 ECIR 2026，但原任务是检索，不是我们的 Hotpot 答案评测。[正式出版页](https://link.springer.com/chapter/10.1007/978-3-032-21300-6_30)
- RRM 是必须排重的近邻；不把其多模态完整系统硬抄为首轮唯一对手。
- 后续 QPP 阶段用相同实际候选池比较选择策略；POST 多轮阶段再引入 ReflectiveRAG/S2G，不把不同检索轮数混在 PRE 表示结论里。

本轮发现 ReFormeR 论文与公开核心实现有差异：论文写训练目标，而公开核心代码走现成 LLM 的选择/应用提示词；其选择器读取首次检索文档。近期应锁作者仓库提交，标成“作者公开代码适配版”，逐项记明差异与成本，不能直接称 query-only、零训练的完整论文复现。作者入口：[ReFormeR](https://github.com/aminbigdeli/ReFormeR)，[核心代码](https://github.com/aminbigdeli/ReFormeR/blob/main/reformer/core/reformer.py)，[论文方法](https://arxiv.org/html/2604.01417v1)。

### 净收益不是尚无人做过的公式

RRM 的组件消融已经比较本题 OQR 与 OQR 加经验，并包含经验生命周期管理。[RRM](https://arxiv.org/html/2607.28156v1)

QCR §5.1 直接使用有记忆减去无记忆的成功差值；其固定已选来源后改变执行端表示，与我们改变选择端可见表示的实验位置不同，但不能据此保证新颖。[QCR](https://arxiv.org/html/2608.12847v1#S5.SS1)

ReMe 已按使用次数和成功比例做效用淘汰，并有无记忆对照；简单的成功计数/遗忘本身不是我们的创新。[ReMe 方法](https://arxiv.org/html/2512.10696v2#S3.SS4)，[ACL 2026 Findings 正式入口](https://aclanthology.org/2026.findings-acl.829/)

更值得验证的窄问题是：**相同历史候选与执行动作下，记录哪些可观察条件，能让选择器更准确地预测该卡相对现场改写的额外收益，同时少误用、少误拒？**

这是研究假设，不是已证明优势。先做表示对照，再做同信息自然段与单项删字段，查看哪些错误真由某条件阻止；若仅更长提示或多候选带来提升，就应如实归因，不能叫条件机制新贡献。逐卡、分情境净收益反馈可作为后续扩展，不在第一轮全部堆上去。

## 15. 是否要用完整 Hotpot train “训练一遍”

不需要。当前冻结大模型参数和 prompt，所谓训练题用途主要是**收集经验**。下载了 90,447 条 train 不意味着必须全部付费跑一遍。训练小选择器是另一阶段。

| 阶段 | 数据 | 用途与限制 |
|---|---|---|
| 已完成来源诊断 | train 内 64 来源 | 得 6 候选；先检查条件质量，不自动扩至 256 |
| 下一步调试 | 隔离的 train 内 8 题 | 修接线、设计分析；不是论文测试成绩 |
| 首轮冻结检查 | 另外隔离的 train 内 24 题 | 冻结视图/规则后检查是否有信号；看过后不再称盲测 |
| 扩大经验/选择研究 | 预划 train 子集 | 画来源题量—效果—费用曲线；保留 selector_train，不先训练大模型 |
| 正式开发集评价 | 官方 dev | 冻结方法和记忆后统一比较；诚实称 dev，不称官方 test |
| 官方测试 | hidden test | 按可用官方提交流程；不用于建库、调参或反馈更新 |

当前 train 内 80%/10%/10% 是我们的内部角色划分，不是 Hotpot 官方规定；见 [冻结名单说明](D:/project/GrowRAG/knowledge/datasets/2026-09-11_完整训练镜像与冻结名单.md)。官方 train/dev 提供答案和句级 supporting facts；公开 fullwiki test 不提供这些评判标签，也不提供 type/level。不能依赖官方题型标签做上线选择输入。[Hotpot 官方格式](https://github.com/hotpotqa/hotpot#json-format)

和别人公平比较时，尽量固定 Reader 模型、题目、语料、检索器、截断、候选数和预算重新运行。论文原分数来自其他模型/语料，不能直接拼进同一排名。若对手原方法依赖训练、首次检索文档或额外经验数据，应保留或明确标注控制版的改动；“换成同一个 Qwen”不自动等于忠实复现。

## 16. 成本与下一步顺序

| BASE/FRESH Reader | 128 | 78,545 | 9,867 | 0.0236026 |
| FRESH 改写 | 64 | 18,514 | 1,528 | 0.0049252 |
| 提卡 | 6 | 1,698 | 881 | 0.0010444 |
| 合计 | 198 | 98,757 | 12,276 | **0.0295722** |

按当批配置输入 0.2 元/百万、输出 0.8 元/百万和 API usage 估算，尚非供应商账单核对。Reader 约占 79.8%。本批没有真实目标题选择、多个历史改写或 QPP 费用。

本地 BM25 不消耗模型 API tokens，但仍有计算时间；未来 embedding、重排或预测若用付费 API，须另外记账。多写 query 的输入可能包含很长历史；3–5 次改写再加 LLM 选择不一定比一次短 Reader 更便宜。须比较实际总成本，而不是只看输出 query 很短。

建议下一步按顺序推进，不同时更改全部模块：

1. 审查 6 张来源卡与当前 FRESH 错例，区分不合法条件、过度泛化、检索负效应和评分表述问题；原结果不改。
2. 固定第一轮 M1/M2/M3/M5 的生成与输入预算，补逐题可读轨迹；用 8 道调试题核查，不提前看 24 题结果。
3. 若加强 FRESH，先在调试协议中独立冻结新版本，保留旧 FRESH，不通过降低对照强度证明记忆。
4. 跑冻结检查后做同信息自然段和删字段分析；优先回答用户已选择的“最少适用条件”。
5. 有信号后再接 QPP 查询池选择；之后才做有限 gap 修复和流式记忆维护。

已有本批总预算 5 元不是每阶段重置 5 元；后续入口需承接或扣除已有账本与保守预留。本轮没有发起新的收费运行。
