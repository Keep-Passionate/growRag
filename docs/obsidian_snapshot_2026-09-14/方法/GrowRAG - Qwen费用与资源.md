# Qwen 模型费用与本地资源核验

## 最需要掌握的 3 点

- 当前北京百炼 Qwen2.5 7B/72B API 已下线，不能拿历史价格做购买建议。
- 先保持当前便宜固定快照做公平对照；本机约16GB RAM、8GB显存，暂时不用租卡。
- 7B可作为后续改写端单变量实验，72B主要是可选离线提炼模型，不需要每题调用。

本篇是运行前的资源核验记录；随后已发生的真实调用与中止，另见 [[GrowRAG - FRESH基线结果2026-09-14]]。下面“未调用”只描述资源核验步骤，不代表整轮工作没有调用API。

> 最需要记住：目前不用为了省钱直接换成 Qwen2.5-72B，也不用现在租大显卡。百炼普通 API 的这两款 Qwen2.5 文本模型已经下线；当前固定 Flash 快照仍很便宜。7B 本地改写值得以后单独测，但要把模型变小造成的质量变化也计入对比。

这批平均一次回答约为一次改写费用的 2.4 倍。但 Reader 只有四个句子的上下文，不能推广成“任何 RAG 都比改写贵很多”。如果一次生成 5 个带长历史的查询，还额外调用选择器，可能比只回答一次更贵。

原批预算上限是整个流程共 5 元，而不是每换脚本就重新有 5 元。旧账本累计保守预留为 0.2289212 元；恢复或扩展实验应汇总已花费和未结清预留，不能只复用一个新建的空账本。

## 3. 本机资源：可开发，不适合 72B

本轮只读硬件检测结果：

- CPU：Intel Core i7-14700HX，20 核、28 线程。
- 系统内存：约 15.78 GiB（通常称 16 GB 内存）。
- GPU：NVIDIA GeForce RTX 4060 Laptop GPU，总显存 8,188 MiB。
- 检查当时空闲显存约 6,361 MiB，会随桌面程序变化。

显存使用 `nvidia-smi` 核对；Windows 视频控制器的 `AdapterRAM` 在这台机器上只报约 4 GB，不能据此误判真实显存。

当前 Python、BM25、小批数据、API 调用和轻量选择器原型不需要租 GPU。7B 的 4-bit 短输入、单并发推理可以作为本机探索项，但现有空闲显存和 16 GB 系统内存都比较紧，尚未验证可稳定运行。不能说“8 GB 一定够所有 7B 部署”。

## 4. Qwen2.5 本地部署需要什么

BF16 可以理解为每个参数大约占 2 字节；4-bit 量化主要压缩权重，但还需要量化元数据、运行缓冲、KV cache（保存本次生成上下文的缓存）。模型权重能放下，不等于长上下文和并发也放得下。

Qwen 官方模型卡报告 7B 实际为 7.61B 参数、72B 为 72.7B 参数。因此仅权重的 BF16 算术下限分别约 14.2 GiB、135.4 GiB；4-bit 的理想下限分别约 3.5 GiB、33.9 GiB，均不包含额外开销。[7B 模型卡](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct)、[72B 模型卡](https://huggingface.co/Qwen/Qwen2.5-72B-Instruct)

官方实际测试条件是 A100 80GB、batch=1、生成 2,048 token；下表选择输入 6,144 token 的结果，显存单位沿用官方 GB。不同运行库、输入长度、并发和显卡不应直接套用其速度或显存。[Qwen2.5 官方部署测试](https://qwen.readthedocs.io/en/v2.5/benchmark/speed_benchmark.html)

| 模型与精度 | 官方测试显存 | 我们若另做本地推理的资源建议（估计，非实测） |
| --- | ---: | --- |
| 7B BF16 | 15.38 GB | 单张 24 GB 显卡，系统 RAM 32 GB；短输入、低并发 |
| 7B AWQ 4-bit | 6.39 GB | 单张 12–16 GB 更宽裕；RAM 32 GB；现有 8 GB 可限长探索 |
| 72B BF16 | 140.00 GB，2 张 GPU 合计 | 2×80 GB 起步，短输入、低并发；RAM 256 GB 较宽裕 |
| 72B AWQ 4-bit | 42.13 GB | 单张 80 GB、RAM 128 GB 较宽裕；48 GB 只可视为紧凑条件方案 |

上述建议是对官方测量加余量的工程估计，不是最低保证，也不用于全参数训练。长上下文、大并发或训练需要重新测算。系统 RAM 取值是我们为加载权重和数据预留的建议，不是官方测出的硬下限。

## 5. “7B 改写＋较强模型回答”值得做吗

值得作为独立对照，但不要同时改变改写算法、改写模型、回答模型和检索器。

建议顺序：

1. 先保持当前固定 API 模型，把更强 FRESH 方法和历史方法跑在相同底座上。
2. 方法与提示词冻结后，只把改写器替换为固定版本的 Qwen2.5-7B-Instruct；Reader 保持相同，单独测 EM/F1、检索收益、失真和成本。
3. 如果使用 4-bit，再另列量化条件；不能把量化 7B 写成 BF16 7B 的完全复现。
4. 只有需要本地 72B Reader 且预算/规模合理时，再考虑租服务器。本轮没有租卡、购买实例、安装推理服务或下载权重。

小模型通常减少本地计算量；是否降低 API 账单取决于具体供应商价格。旧模型、参数更少不自动意味着 API 更便宜。若为了论文复现改用其他供应商，需另核对可用性、量化、模型版本和价格，不能自动复用当前密钥或认定后端等同。

## 6. 成本研究应该如何记账

建议每题保留分阶段实测值，而不是只记最后一次回答：

| 阶段 | 必记内容 |
| --- | --- |
| 经验准备 | 提卡、整理模式、标注选择训练数据的调用和耗时 |
| 候选改写 | 每条候选的来源、模型、输入/输出 token、费用、生成耗时 |
| 选择/QPP | 选择器推理费、耗时，特征是否需要先检索 |
| 检索 | 实际检索次数、CPU/向量服务耗时；API 嵌入/排序费另记 |
| 最终回答 | Reader token、费用、耗时、成功/失败状态 |
| 额外对照 | 为知道未选候选表现而运行的额外 RAG：属于实验审计成本 |

报告同时给出：离线建库总成本、真实实验总成本、单条策略的应用成本、端到端延迟和检索次数。只使用一个候选的应用成本不能混入所有候选的离线审计费用；反过来也不能把审计调用当作免费。并行阶段延迟用真实墙钟时间，不能直接把所有请求耗时相加当端到端延迟。API 等待时间也不等于模型纯计算时间。

提前选择与运行后选择应共用同一候选池和相同底座：前者在一次 RAG 前选择，后者需为更多候选支付检索/回答费。不能用最终答案或 gold 给提前选择器提供特征。

## 7. 本轮核验边界

- 使用官方公开资料、本机只读硬件信息、现有预算账本。
- 未读取 API key，未发送模型调用，未改运行配置。
- 上述本地资源建议还不是本机部署结果；不据此承诺吞吐量。
- API 价格和可用性可能变化；每次正式大批量运行之前再次核对固定模型 ID、地域和计费阶梯。
