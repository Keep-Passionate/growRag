# 查询变体、经验卡、生命周期与双路线

更新日期：2026-08-19  
状态：本轮讨论后的当前设计；真实数据实验前仍可调整

## 1. Query variant 是什么

**Query variant（查询变体）**是：针对同一个信息需求，实际送给检索器的另一种查询表达。

例如原问题：

```text
Who was born first, Alice or Bob?
```

可以产生几种 query variant：

```text
改写：Compare the birth dates of Alice and Bob
扩展：Alice Bob birth dates date of birth
分解：Alice birth date ; Bob birth date
消歧：Alice [full identity] birth date
```

它不是答案，也不是把历史答案放进提示词。一个问题可以有多个候选 variant；选择器决定使用原查询还是其中一个 variant。

本项目必须区分三件东西：

1. 来源题上观察到的 `q_s → q_s'`；
2. 从这次变化中保存的修复经验；
3. 将经验应用到当前题后得到的 `q_t'`。

来源题的 `q_s'` 不能原样复制给目标题，否则会带入错误实体。

## 2. 两条路线

### 路线 A：检索前可信复用（当前主线）

```text
当前问题
  → 找历史经验
  → 判断历史可靠度、环境兼容性和当前适用性
  → DIRECT 或 REUSE
  → 第一次正式检索
```

优点：

- 轻量，可作为任何 RAG 前面的 sidecar；
- 可以避免一次失败检索和一次现场反思；
- 关闭后严格退化为原始 RAG；
- 不修改索引，不污染文档表示。

局限：

- 还没看当前检索结果，不知道究竟缺了哪条证据；
- 当前适用性只能从问题和环境预测，不能保证；
- 为了安全会拒绝一些本可受益的问题。

### 路线 C：首次检索后的缺口修复（备选/第二阶段）

```text
当前问题
  → DIRECT 首检
  → 判断证据是否充分，并结构化描述缺口
  → 找历史“缺口 → 修复动作”经验；若无合适经验则现场修复
  → 定向构造下一查询并二次检索
```

优点：

- 有真实证据上下文，能更准确地说明“缺什么”；
- 可以定向补桥接实体、属性、关系或证据跨度；
- 不必对首检已经充分的题做任何改写。

局限：

- 至少已经付出一次检索成本；
- 架构和日志更复杂，必须控制多轮预算与上下文噪声；
- “判断充分 → 生成缺口 → 再检索”本身已被 ReflectiveRAG、S2G-RAG 等覆盖，不能单独称为创新。

### 与 ReflectiveRAG、S2G-RAG 的实质差异

- ReflectiveRAG：本题内先检索，再由小模型判断 `Sufficient/Refine`，不足时现场改写，并对证据去噪；不持久保存跨题查询修复经验。
- S2G-RAG：本题内维护证据上下文，由训练过的 S2G-Judge 输出充分性和结构化 gap items；gap 包含 `category/target/slot/description`，随后确定性构造下一查询，并做句子级证据提取；不管理跨题经验的可靠度、衰减和复用伤害。
- GrowRAG 路线 C 若继续：创新对象不能只是“再做一个充分性判断器”，而应是**跨题、可验证的 gap→repair 经验是否能安全替代部分现场修复**，以及何时退回 fresh repair。

## 3. S2G 风格经验卡，但不照搬当前题 gap

来源经验卡现在包含：

```text
source_query / transformed_query
diagnosed_failure       来源题为什么需要修复
gap_categories          bridge_entity / attribute / relation / evidence_span / other
atomic_units            实际查询修复操作
applicability_signature 正向适用条件
contraindication_signature 禁用条件
provenance + environment
独立目标题上的 benefit/harm 记录
```

S2G 的 gap item 描述的是**当前题在当前证据上下文中**缺什么；GrowRAG 来源经验卡描述的是**历史上哪类缺口曾被哪种变换修好**。路线 C 可以把两者连接起来：

```text
当前 gap item → 召回相同 gap 类经验 → 应用其 atomic repair → 当前题新查询
```

路线 A 还没看到证据，因此只使用问题结构条件和禁用条件，不能声称已知道当前证据缺口。

## 4. 为什么不能只把“不可靠经验”拒绝写入

一条经验在来源题成功，只能证明它对来源题有效；未来仍可能因为以下原因失效：

- 新题表面相似，但关系结构不同；
- 原查询本来已经足够，额外改写反而漂移；
- corpus、index、retriever 或文本分析方式变化；
- 经验只对某个问题族有效；
- 曾经有效，但数据分布随时间变化。

因此使用三层隔离：

1. `candidate`：来源题成对改进，只能 shadow 验证；
2. `active`：独立问题上积累了足够收益和低伤害证据，才可进入服务候选；
3. `quarantine/retired`：暂停或退出自动复用，但保留审计记录，避免以后重新学习同一个坏经验。

“不存”适用于未通过来源写入门的普通失败；“保留但不可调用”适用于已进入实验、需要审计和复现的经验。

## 5. 衰减和 Top-K 管什么

参考 RRM 的使用反馈与时间衰减思想，我们增加一个非破坏性的热记忆视图：

```text
priority_base = benefit_rate × (1 − 条件破坏率的保守上界)
priority = priority_base × 0.5^(距上次验证的步数 / half_life)
```

- `reliability` 是历史统计证据，不随时间凭空被改写；`priority_base` 只是排序启发式，不是校准概率；
- `priority` 只决定谁进入 hot Top-K；
- 仅仅“被调用”不会刷新验证时间，必须得到新反馈才会刷新；
- Top-K 之外进入 cold，过低进入 expired；都不删除原始记录。
- hot Top-K 会造成冷经验缺少新反馈，因此必须另设与线上选择解耦的周期性 shadow/revalidation 流；第一版不做有风险的线上随机探索。

这不是 EMA。GAM-RAG 使用的是受不确定性控制、受 Kalman 思想启发的 gain update；RRM 明确使用频率、复用反馈和时间衰减；ERM 提供写入时 correctness gate，但没有我们的逐题读取拒绝门。

第一篇论文中，衰减与 Top-K 更适合作为生命周期模块或消融，而不是核心创新主张。

## 6. 环境是否一致，如何减少变量负担

代码仍保存完整指纹，但概念上只看四份契约：

1. **知识契约**：corpus ID/version；
2. **检索资产契约**：index ID/version 或内容 hash；
3. **检索逻辑契约**：retriever ID/version；
4. **文本处理契约**：analyzer/tokenizer ID/version。

查询变换的 applier/prompt 版本单独作为执行 provenance 检查，不混入检索环境。

提供两种模式：

- `strict`：八个检索字段全一致；主实验默认使用，归因最清楚；
- `tiered`：corpus/index/retriever ID 是硬约束，retriever/analyzer 版本差异作为软告警并扣分；仅在开发集证明安全后使用。

这些字段由建索引和运行配置自动生成，不应要求模型自己猜。

## 7. 如何判断当前适用性

适用性与历史可靠度分开：

1. 用来源 query 相似度召回 top-m 历史卡；
2. 检查当前题是否覆盖正向条件，例如 `comparison + two_entity`；
3. 检查是否触发由纯 query 信息得到的禁用条件，例如 `single_entity`、`non_comparison`；
4. 检查环境与查询预算；
5. 只在历史风险与当前适用性都过阈值时复用。

当前代码要求请求携带结构 signatures。这是可运行接口，但**自动产生这些 signatures 的方法尚未定稿**。可选路线：

请求协议会同时记录 signature extractor 的 ID、版本和 `query_only` 输入范围；混用不同抽取协议或让抽取器读取检索结果会直接拒绝运行。

- 规则抽取：最容易、最可解释，覆盖有限；
- 冻结 LLM 输出结构标签：无需参数训练，成本与稳定性需测；
- 小型分类器：需标注/蒸馏，但可校准且运行便宜；
- 检索后 S2G-style gap judge：信息最充分，但不再是纯检索前层。

第一阶段建议先用数据集可推导标签和人工审计的小样本验证现象，再比较规则与冻结 LLM；不要一开始训练复杂 controller。

## 8. 安全不能一刀切

安全门使用两个可解释旋钮：

- 最大历史风险上界；
- 最小当前适用性。

在 calibration/dev 上扫一组阈值，得到 risk–coverage 曲线：

- 门越严：harm 通常更低，但复用 coverage 也更低；
- 门越松：覆盖更多，也可能破坏更多原本正确的查询。

最终选择的是一个**操作点**，不是宣称“越严越好”。操作点必须在看 test 前冻结。代码已支持离线阈值扫描，分别报告 coverage、benefit、harm、条件破坏率、repair rate 和 mean gain。

## 9. 当前建议

第一篇继续以路线 A 为主，因为容易做出最小可证伪实验。路线 C 保留为强基线和自然的第二阶段：若检索前适用性预测上限太低，就转向“结构化缺口 + 历史修复经验 + fresh fallback”。

真正共同的研究问题是：

> 历史修复经验在什么时候足以替代现场修复，什么时候应该保持原查询或重新诊断？

但两条路线的输入信息和成本不同，实验中必须分开报告，不能混成同一个方法结果。
