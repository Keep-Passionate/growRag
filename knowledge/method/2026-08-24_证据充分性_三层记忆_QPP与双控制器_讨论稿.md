## 0. 先给结论

GrowRAG v1 不把“问题看起来难不难”当作路由依据，也不把一次 LLM 自信判断当作证据充分。推荐流程是：

```text
原问题 q0
  -> BASE 检索
  -> 将问题拆成可核对的信息需要，并建立“需要—证据”支持图
  -> SUPPORTED：回答
  -> REPAIRABLE_GAP：选择可信且适用的历史修复，或做本题 FRESH 修复
  -> CONFLICTED_OR_UNCERTAIN：继续核验；无安全进展则弃答
```

三层记忆保留，但各层必须承担不同作用：

- `QueryEpisode`：这个问题具体发生了什么；
- `DocumentSession`：如何在这一篇、这一版本文档里找到所需内容；
- `ExperienceCard`：跨文档仍可能成立的查询修复原则。

这三层本身不是论文创新。最可守的中心问题是：

> 如何用同题 BASE/REUSE 配对结果，分别估计历史经验的可靠性与当前适用性，并显式限制“BASE 原本正确、复用后反而错误”的风险？

## 1. 当前代码到底已经有什么

当前 M0 代码已经实现：

- `QueryEpisode`、turn、结构化 gap、evidence pointer 和停止原因的数据合同；
- `sufficient / insufficient / unknown` 三值字段及若干一致性约束；
- BASE/REUSE/FRESH 配对验证事件和版本化 `ExperienceCard` 的基础结构。

当前代码**尚未实现**：

- 真正读取证据并作判断的 sufficiency judge；
- BM25/稠密检索器和回答器的端到端连接；
- QPP、经验匹配、在线 RetrievalController；
- 本文提出的新 `DocumentSession` 文档级内容；
- 下文的完整停止规则。

因此，下面是下一版架构建议，不是对已实现功能的夸大描述。

## 2. 如何判断证据是否充分

### 2.1 “证据充分”不是“答案看起来像对的”

推荐定义：对原问题 `q0` 的每个必要信息点，都能指向当前新检索到的证据；证据之间没有尚未解决的冲突；据此可以生成有来源支撑的答案。

判断步骤：

1. 把 `q0` 拆成最小的 `information needs`，即回答它必须知道的实体、属性、关系或桥接事实。
2. 为每个 need 建立 `support_map`，只允许引用当前累计证据中的具体片段。
3. 标记每项为 `covered / partial / missing / conflicted`。
4. 只有全部必要项 `covered` 且没有未解决冲突，才进入 `SUPPORTED`。
5. 若能明确说出缺口，进入 `REPAIRABLE_GAP`；若证据互相冲突、judge 无法稳定判断或问题本身含糊，进入 `CONFLICTED_OR_UNCERTAIN`。

建议的可审计状态：

```yaml
EvidenceState:
  label: SUPPORTED | REPAIRABLE_GAP | CONFLICTED_OR_UNCERTAIN
  needs:
    - need_id:
      description:
      required: true
  support_map:
    - need_id:
      status: covered | partial | missing | conflicted
      evidence_refs: []
  gaps:
    - category: bridge_entity | attribute | relation | evidence_span | other
      target:
      slot:
      description:
  contradictions: []
  progress:
    new_unique_evidence_count:
    gaps_closed: []
    duplicate_ratio:
```

它可暂时映射到当前 v0 字段：

- `SUPPORTED -> sufficient`
- `REPAIRABLE_GAP -> insufficient`
- `CONFLICTED_OR_UNCERTAIN -> unknown`

### 2.2 没有 gold 时怎么办

运行时通常没有 gold，不能先知道正确答案再决定是否继续检索。v1 应使用冻结 prompt 的 context-only judge：它只能核对 `q0 + 当前证据`，不得用模型参数知识补齐证据。gold 只在离线开发集上用于：

- 测 judge 把 sufficient 判错为 insufficient、或反过来的概率；
- 校准阈值和停止规则；
- 比较 BASE/REUSE/FRESH 的真实收益与伤害；
- 后续蒸馏一个小 judge。

这不是强化学习的前置条件。先把监督式离线评估和冻结 prompt 跑通，再决定是否训练。

### 2.3 参考论文做了什么

| 工作 | 它怎样判断 | 可借鉴 | 不能直接照搬的不足 |
|---|---|---|---|
| [S2G-RAG，ACL 2026 Long](https://aclanthology.org/2026.acl-long.1185/) | judge 读取原问题与累计句级证据，输出二值充分性和 `category/target/slot/description` gap；训练标签由 teacher rollouts 产生，再 LoRA 训练 3B judge | context-only、累计证据、结构化 gap | 只分充分/不足；没有专门的冲突态；主要按充分或轮数预算停止 |
| [ReflectiveRAG，EACL 2026 Industry](https://aclanthology.org/2026.eacl-industry.27/) | 小模型看原问题、当前 query 和检索文档，输出 `Sufficient/Refine`；不足时产生 reformulation/subquery | 本题内 `不足 -> 改 Query`，以及边际改进思想 | 论文的边际停止描述与可复现算法细节不够完整，仍需硬预算兜底 |
| [SIM-RAG，SIGIR 2025](https://doi.org/10.1145/3726302.3730018) | critic 看问题、累计上下文和候选答案/理由，给 Accept/Reject；Reject 后再检索 | 可作为答案后支持校验 | 容易把“模型答对”与“检索证据充分”混在一起，且训练依赖 gold |
| [Self-RAG，ICLR 2024](https://openreview.net/forum?id=hSyW5go0v8) | reflection token 判断是否检索、文档相关性、生成片段是否受支持、答案效用 | 回答生成后的 support/utility 校验 | 不是专门的、回答前的证据集合覆盖判断 |
| [CRAG，arXiv](https://arxiv.org/abs/2401.15884) | 对 query-document 相关性作 Correct/Incorrect/Ambiguous 判断 | 检索质量信号 | 相关不等于“整组证据足够回答” |
| [SURE-RAG，arXiv 预印本](https://arxiv.org/abs/2605.03534) | 把候选答案拆成 claims，并判断 Supported/Refuted/Insufficient | 冲突和 claim-level 支持检查 | 主要决定回答/弃答，不是结构化 gap 的迭代修复 |

推荐组合不是简单投票，而是两个不同位置的门：

1. **回答前 Coverage Gate**：S2G 风格的 needs-support map，决定 ANSWER/REPAIR/UNCERTAIN；
2. **回答后 Support Check**：Self-RAG/SURE-RAG 风格，确认最终答案中的关键 claim 确实由证据支持。

第一道门负责路由，第二道门只是安全检查。v1 可以先实现第一道，第二道作为实验开关，避免一开始过重。

## 3. FRESH_REPAIR 到底是什么

是的，它就是“同一个原问题内部，多轮检索修复”的那条路线，最接近 ReflectiveRAG 和 S2G-RAG。但它不是机械地递归改写上一条 query：

```text
q0
 -> BASE(q0)
 -> 对 q0 与累计证据判断缺口 g1
 -> 由 q0 + g1 + 已有证据生成 q1
 -> 检索并更新累计证据
 -> 再判断 q0 的剩余缺口 g2
 -> ...
```

每轮始终以原问题 `q0` 为目标，上一轮 query 只是历史，避免越改越偏。FRESH 只能使用当前 episode 的问题、证据与 gap，不调用跨题 ExperienceCard；REUSE 则让一张历史卡约束如何生成本轮 query。

### 3.1 完整终止条件

建议 v1 采用可观测的组合条件，而不是一个含糊的“边际增益分数”：

1. **成功停止**：所有必要 needs 被覆盖、无未解决冲突；回答后关键 claims 通过支持检查。
2. **硬预算**：默认总共最多 4 次检索，即 1 次 BASE + 最多 3 次 repair；同时限制 token、延迟和累计文档数。数值只在 dev 校准。
3. **无进展**：连续 2 轮没有关闭任何 gap，也没有新增独立支持证据。
4. **循环**：规范化 query 重复、同一 gap signature 重复，或检索证据高度重复。
5. **持续冲突**：连续修复未减少关键矛盾。
6. **候选无效**：拟执行 query 与已有 query 重复，执行前即拒绝。
7. **REUSE 失约**：复用结果没有满足卡片的 evidence contract；当前 episode 不再重复用同一张卡，最多切换一次 FRESH。
8. **预算耗尽仍不足**：记录 `STOP_ABSTAIN`，不能把“被迫生成答案”伪记成充分。

`gaps_closed`、`new_unique_evidence_count`、`duplicate_ratio` 和 `contradictions` 是边际进展的四项原始观测，日后阈值变化时仍能重算。

## 4. REUSE 如何选择最适用的历史经验

### 4.1 为什么“只存成功经验”仍不够

一条历史修复答对，不代表它导致了答对：BASE 可能本来也能答对；同一文档的十个近重复问题也不能算十次独立证据；语料、缺口或检索能力变化后，原来正确的模式可能误导当前问题。

因此必须分开两个问题：

- **Reliability（历史可靠性）**：这张卡在过去的独立问题、独立文档中，相比 BASE 是否反复带来净收益；造成过多少 `BASE correct -> REUSE wrong` 伤害？这是较慢更新的卡片级历史属性。
- **Applicability（当前适用性）**：这张可靠卡是否适合眼前的 `q0 + gap + 环境`？这是每个新问题都要重算的瞬时关系。

一张“出生地属性修复”卡可以历史上非常可靠，但对一个药物副作用问题完全不适用；另一张卡在措辞上很像当前问题，却只在一个历史样本成功过，适用性像、可靠性仍不足。二者不能揉成一个 confidence。

### 4.2 建议的四级选择

```text
候选 ExperienceCards
  1. Reliability hard gate
  2. Applicability hard constraints
  3. structured match + QPP 排序
  4. 执行后的 evidence contract 验证
```

1. **可靠性硬门**：至少若干独立 paired-benefit；伤害率上界低于阈值；卡片处于 active；来源与版本完整。
2. **适用性硬约束**：repair stage、gap 类型、required capabilities、文档版本/语料范围兼容；不能触发 contraindications；不能把历史实体或答案泄漏进新题。
3. **软匹配排序**：
   - 原问题语义与 query pattern；
   - 当前 `gap category/target/slot` 与 gap pattern；
   - repair intent 与所需 action；
   - 已知文档时的 DocumentSession 局部提示；
   - QPP 对候选 query 的预期检索质量和额外成本。
4. **履约验证**：执行后必须真的填补目标 gap、带来新支持证据且不引入冲突。预测的 applicability 不能代替实际结果。

[RRM（arXiv 预印本）](https://arxiv.org/abs/2607.28156) 已经保存 task type、applicability conditions、required evidence、retrieval strategy、undesirable behaviors 和 query-adjustment patterns，并做衰减、合并和裁剪。它公开版本没有给出足够可复现的 applicability 量化细则，也没有把“历史可靠性 × 当前适用性 × 配对伤害”明确建成双轴门控。这是我们的切口之一，但正式投稿前仍需持续核查后续版本。

## 5. QPP、BM25 与查询动作

### 5.1 BM25 是什么

BM25 是经典的稀疏词项检索排序方法。它主要看：

- query 与文档是否共享词；
- 稀有词比常见词更重要（IDF）；
- 一个词重复很多次后收益逐渐饱和；
- 对文档长度做归一化。

它不需要训练神经网络或生成 embedding。精确人名、术语和编号通常很强；同义表达和深层语义较弱。因此 expansion 可能帮助 BM25 补词，但无节制扩写也会稀释主题。

GrowRAG 中 BM25 有两个角色：可复现的基础 retriever，以及为检索前 QPP 提供 IDF、查询清晰度等便宜统计。它不是充分性 judge，也不是答案评价器。

### 5.2 QPP 放在哪里

QPP（Query Performance Prediction）是在没有当前题 relevance gold 的情况下，预测某条查询可能取得怎样的检索表现。[SIGIR 2026 的 query-variant 选择工作](https://doi.org/10.1145/3805712.3808571) 比较了：

- 检索前 QPP：只看 query 和语料统计，便宜；
- 检索后 QPP：需要先取得 ranked list，再看分数分布/clarity，成本更高。

它还显示 retrieval 最优的 variant 不一定让最终答案最优。因此 QPP 只能是当前候选排序特征，不能证明经验可靠、证据充分或答案正确。

推荐 v1：BASE 失败后生成少量候选，把原 query 也作为 `KEEP` 对照；用便宜的 pre-QPP + applicability + reliability 选一个。post-QPP 主要用于离线基线/分析，避免为了“选择”先执行所有候选。

### 5.3 Expansion 与 LLM rewrite 的关系

用户的上位理解是对的：它们都可以放在 Query Transformation 下。但二者不在同一分类轴上：

- `LLM rewrite` 说明**谁/什么方法生成**变换；
- expansion、paraphrase、decomposition、HyDE 说明**做了什么**。

建议不要用一个扁平动作表，而用两个维度：

```yaml
QueryDecision: KEEP | TRANSFORM

transform_form:
  PARAPHRASE | EXPAND | DECOMPOSE | HYDE

repair_intent:
  DISAMBIGUATE | ADD_CONSTRAINT | BRIDGE_ENTITY |
  FILL_ATTRIBUTE | FILL_RELATION | EVIDENCE_FOCUS
```

- `PARAPHRASE`：换表达，信息需求基本不变；
- `EXPAND`：保留核心 query，加入术语、实体或伪文档；
- `DECOMPOSE`：变成多个子查询，会改变轮数和证据聚合，输出应是 query list/plan；
- `HYDE`：生成假想文档并编码去做稠密检索，严格说是检索表示变换，不只是改写字符串。

同一个修复目的可以由不同形式完成，例如消歧可以用 paraphrase，也可以用 expansion，所以必须把“形式”和“目的”分开。[Query Rewriting in RAG（EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.322/)、[Query2doc（EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.585/) 和 [HyDE（ACL 2023）](https://aclanthology.org/2023.acl-long.99/) 分别是重要基线。[ReFormeR（ECIR 2026）](https://doi.org/10.1007/978-3-032-21300-6_30) 已经做过“选择改写模式后约束生成”，所以动作词表不是我们的创新。

## 6. 三层记忆：每层只保存它该知道的东西

[Useful Memories Become Faulty When Continuously Updated by LLMs（arXiv 预印本）](https://arxiv.org/abs/2605.12978) 的重要启示是：raw episodes 与 consolidated abstractions 都需要保留，反复让 LLM 覆盖抽象记忆可能使原来有用的内容变坏。GrowRAG 在此基础上加入严格的文档局部层，但三层结构本身也已受到 [SegMem-RAG（AAAI 2026）](https://ojs.aaai.org/index.php/AAAI/article/view/40320) 等工作的明显覆盖，不能宣称首次。

### 6.1 QueryEpisode：问题级、具体、不可变

保存：

- 原问题、每轮实际 query 和动作；
- 每轮针对的 need/gap；
- 新检索证据指针、支持图与冲突；
- BASE/REUSE/FRESH 路径、成本、停止原因；
- 最终结果及延迟到来的 gold/人工/judge 验证事件。

理由：这些是“这个问题实际发生了什么”的原始事实，必须能审计和做同题配对归因。它可访问多篇文档，绝不等于单文档。

不保存：完整隐藏 CoT、复制的文档正文、把历史答案当当前事实。

### 6.2 DocumentSession：单文档、局部、版本化冻结

严格定义：一个 `DocumentSession` 只对应 `document_id + exact document_version/content_hash`。它不是聊天 session，也不是 episode 文件夹。

建议保存：

| 内容 | 为什么属于文档层，而不属于另外两层 |
|---|---|
| `document_id / version / content_hash` | 保证提示只对这一版文档生效；文档改版后不能静默沿用 |
| 文档局部 alias、缩写、术语与实体表达 | 它们可帮助同一文档后续 query grounding，但跨文档往往不成立 |
| section/chunk landmarks 与 need/gap 类型的映射 | 记录“这篇文档的某类信息通常在哪里”，不是某一问题的完整轨迹，也不是跨文档规则 |
| `repair form × gap` 的局部 benefit/harm 统计 | 判断某种修复在本文件内是否稳定，不把近重复问题误当成跨文档验证 |
| ambiguity / failure hotspots | 如术语歧义、表格引用、附录跨引等，是本文档特有检索难点 |
| 支撑它的 episode-turn refs | 能回到具体问题和证据，不复制 episode |
| opened/frozen、parent version、lifecycle | 文档结束后冻结；内容更新时建立 successor，不覆盖旧版本 |

明确不保存：

- 完整问题轨迹或答案（属于 QueryEpisode）；
- 可跨文档的抽象修复法则（属于 ExperienceCard）；
- 文档正文、完整摘要或反复覆盖的 LLM 总结；
- 用来直接回答当前问题的历史事实。

调用规则：只有当前检索已定位到该文档、或任务明确指定这篇文档时，才按精确版本使用其 DocumentSession。它不是全局语义记忆池。

### 6.3 ExperienceCard：跨文档、抽象、可拒绝

保存：

- query pattern 与结构化 gap pattern；
- preconditions、contraindications 和 required retriever capabilities；
- repair intent、transform form、slot template；
- 执行后必须满足的 evidence contract；
- paired benefit/harm 的可靠性账本；
- 来源 episode-turn、独立问题/文档计数；
- parent versions、active/quarantine/retired serving state 和预期成本。

理由：在线需要的是一个小而可核验的“何时用何种修复”的跨文档程序规则，而不是搬运历史 query 字符串或答案。具体历史 query 仍由来源指针保留在 QueryEpisode 中。

一行区分：

```text
QueryEpisode    = 这道题发生了什么
DocumentSession = 在这一篇文档里怎样找
ExperienceCard  = 跨文档仍可能怎样修
```

## 7. 具体—抽象双表示、版本化晋升、在线库与审计库

### 7.1 具体—抽象双表示

- 具体表示：`q0 -> q' -> evidence -> outcome`，原样冻结在 QueryEpisode；
- 半抽象表示：这篇文档的术语/位置/失败热点，放在 DocumentSession；
- 抽象表示：去实体化的 gap 条件、修复 operator 和 evidence contract，放在 ExperienceCard。

只存具体历史会过拟合旧实体；只存抽象总结会丢失例外和来源。双表示让在线调用轻量，同时出错后仍能回查。

### 7.2 来源保留的版本化晋升

例子：

```text
冻结 Episode E1/E2
  -> Candidate Card C@1（指回具体 turn）
  -> 新的独立 paired benefit 验证
  -> Active Card C@2，parent=C@1
  -> 与另一卡合并
  -> C@3，parents=[C@2, D@2]
```

旧版本不被 LLM 覆盖；合并、修正、降级均生成事件或新版本。这样能审计、回滚，并检验哪一次抽象导致损坏。

### 7.3 “在线可用库”与“审计档案库”

- **在线可用库（serving memory）**：当前控制器有资格召回、并可能影响新 query 的小型 active 集合；包括 active ExperienceCards，以及精确版本匹配的 DocumentSessions。
- **审计档案库（cold archive）**：保存冻结 episodes、失败轨迹、隔离/退役卡和旧版本；默认不进入在线 prompt/检索。这里的 cold 是逻辑角色，不要求真的放到廉价冷存储硬件。

`forget/retire` 的默认含义是从在线可用库移除，不物理删除原始记录。这样既减少在线噪声，又保留负例、审计和回滚能力。

## 8. Controller 不是“失败后的两条分支”

推荐拆成两个时间尺度不同的 controller。

### 8.1 在线 RetrievalController

观察 `EvidenceState + budget + reliability/applicability candidates + QPP`，每轮选择：

```text
ANSWER
REUSE_TRANSFORM
FRESH_TRANSFORM
STOP_ABSTAIN
```

REUSE/FRESH 只是证据不足后的两种修复来源；ANSWER 和 STOP 同样是控制动作。首版用冻结规则/prompt，不训练。后续才可能蒸馏逻辑回归、树模型或小模型。

### 8.2 异步 MemoryLifecycleController

回答结束后或定期执行：

```text
NOOP
CREATE_CANDIDATE
PROMOTE
MERGE_AS_NEW_VERSION
QUARANTINE
RETIRE_FROM_SERVING
```

`QueryEpisode` 每题结束自动冻结，不需要 controller 决定是否保存。失败 episode 进审计档案，不进 serving。

[MemCon（arXiv 预印本）](https://arxiv.org/abs/2607.13591) 的动作包括 Retrieve、PlanInject、Re-Retrieve、Consolidate、Forget、NoOp；其中 Consolidate 是调用后端维护钩子，并不等于论文已规定一个统一的“重复经验合并算法”。MemCon 把在线调用与维护放进一个 MDP。GrowRAG 分成两个 controller，是为了分离回答质量反馈与长期记忆质量反馈，也让消融和归因更清楚。

## 9. 我们到底创新在哪里，还是只是拼接

如果论文写成“三层记忆 + QPP + gap rewrite + controller”，审稿人完全可以说这是 RRM、S2G-RAG、ReFormeR、MemCon、SegMem-RAG 与 Useful Memories 的拼接。以下都不能单独作为创新：

- 三层或双层记忆；
- expansion/paraphrase/decomposition 动作表；
- QPP 选 query variant；
- applicability conditions；
- 衰减、top-k、merge、forget/noop；
- 充分性不足后继续检索。

建议把所有模块围绕一个中心研究问题组织：

> **Paired, harm-aware safe transfer of query repairs**：同一新问题上，历史修复何时真的比冻结 BASE 或本题 FRESH 修复有净收益，并且怎样显式控制负迁移？

可检验贡献：

1. **BASE/REUSE/FRESH 同题、同预算配对归因**：不能因为 treatment 答对就给经验记功；必须证明相对 BASE 的净变化。
2. **Reliability × Applicability 双轴门控**：历史跨题收益/伤害与当前 query-gap-env 匹配分开估计，任一不过关都不复用。
3. **结构化 gap 与 evidence contract**：不只预测“看起来适用”，执行后还要证明修复填补了目标缺口。
4. **无伤害目标与自然退化**：显式报告并约束 `P(REUSE bad | BASE good)`；没有安全经验时退回 FRESH 或普通 RAG，而不是为了调用记忆而调用。
5. **保留来源的版本化验证**：所有可靠性统计能回到不可变 episode 和 paired event，支持隔离与回滚。这是保证前四点可信的机制，不是单独卖“版本管理”。

对应研究问题建议：

- RQ1：paired-benefit 晋升是否比 success-only 存储显著减少 harmful reuse？
- RQ2：分离 reliability/applicability 是否优于相似度、单 confidence 或 reliability-only？
- RQ3：DocumentSession 局部约束是否减少“同文档有效、跨文档误用”的负迁移？
- RQ4：随着 BASE 模型增强，系统能否降低经验调用率但保持更高的每次调用收益和近零伤害？

这是截至 2026-08-24 检索范围内较可守的切口，不能在投稿前声称“绝对首次”；尤其要持续追踪 RRM 后续版本。

## 10. 强模型更少调用经验，研究还有没有意义

有意义，但论文目标必须从“尽可能多调用记忆”改成“只在有净收益时调用”。强模型可能让简单问题的修复空间变小，这恰好要求 controller 学会更多 `ANSWER/NOOP`。高调用率不是成功；以下才是：

- 被选择调用时的正收益率提高；
- `BASE correct -> REUSE wrong` 接近零；
- 额外 token、检索次数和延迟下降；
- BASE 变强后调用率自然下降，而不是仍强迫使用记忆；
- 在多跳、歧义、长文档或检索瓶颈问题上仍捕获一部分 oracle headroom。

MemCon 的公开预印本并没有得出“强模型使经验无意义”；它反而报告在较强 backbone 上仍有收益。更稳妥的做法是先做 headroom gate：

```text
小/中/强 generator × 单纯/较强 retriever
BASE | always-reuse | selective-reuse | fresh-only | oracle
```

同时测 `BASE错->REUSE对`、`BASE对->REUSE错`、调用率、每次调用净收益、成本和 oracle 上限。如果连 oracle query repair 都不能改善强设置，就应换到更难的数据/检索环境，而不是训练复杂 controller。

## 11. 等待确认的默认方案

为避免给用户过多微小选择，建议直接采用以下默认值；只需确认整体是否同意：

1. 主路由使用三态 EvidenceState；回答前 coverage gate 为必需，回答后 support check 先作为可开关安全项。
2. `DocumentSession` 严格绑定一篇文档的精确版本，保存局部术语、位置、热点和局部动作统计；不存文档总结/答案。
3. 线上控制器四动作，记忆维护异步六动作；v1 冻结规则和 prompt，不训练。
4. BASE 后总检索上限暂设 4 轮，并同时启用 success、no-progress、cycle、conflict、budget 五类停止。
5. QPP 是候选排序特征；动作接口为 `KEEP/TRANSFORM + form + intent`。
6. 论文中心贡献锁定为“同题配对、伤害感知的查询修复安全迁移”；三层记忆、QPP 与动作库只作为实现这项研究问题的支撑。

确认后再把 Schema v1 落到代码，避免讨论期间反复重写实现。
