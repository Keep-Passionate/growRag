# GrowRAG 双层记忆与结构化修复（讨论稿）

更新日期：2026-08-21
状态：历史讨论稿；2026-08-22 已选择方案 B，当前权威决策见 `knowledge/decisions/2026-08-22_方案B可信自适应查询修复_已确认.md`

## 1. 先区分论文原意与我们的延伸

《Useful Memories Become Faulty When Continuously Updated by LLMs》区分的是两种互补记忆：

- `episodic traces`：保留“当时发生了什么”的原始轨迹；
- `consolidated abstractions`：从多条轨迹中归纳出的可复用抽象经验。

论文的核心警告是：持续让 LLM 覆盖式地改写 consolidated memory，可能使原本有用的记忆退化，甚至低于 no-memory；因此原始 episode 应保留为一等证据，consolidation 应被显式门控，而不是每次交互后自动执行。它**没有直接提出**“跨文档长期记忆 + 单文档短期记忆”。后者是 GrowRAG 可以据此发展出的架构解释。

一手来源：https://arxiv.org/abs/2605.12978

## 2. 推荐的两层，不把局部层锁死为单文档

### 2.1 当前任务局部记忆（Local Episode Workspace）

作用域是一次问题求解过程，可以只涉及一篇文档，也可以涉及 HotpotQA/2Wiki 所需的多个文档。

建议保存：

- 原问题 `q0`；
- 本题已经执行过的查询；
- 每轮检索到的文档 ID、句子级证据与来源指针；
- 当前结构化失败状态；
- 当前缺口 `gap_items`；
- 本轮新增证据、重复率、充分性与剩余预算；
- 当前动作是 `ANSWER / REUSE_REPAIR / FRESH_REPAIR / STOP_ABSTAIN`。

生命周期：创建于当前问题开始，结束时冻结为不可变 episode；默认不直接参与未来回答。

### 2.2 跨任务长期程序记忆（Global Procedural Memory）

它不保存历史答案或历史证据正文，而保存“怎样修复检索”。

建议经验卡：

- `task_type`：来源问题类型；
- `diagnosed_failure`：来源失败原因；
- `gap_categories`：缺少桥接实体、属性、关系、证据跨度等；
- `required_evidence`：什么证据才算修好；
- `repair_operator`：分解、补实体、补关系、消歧、约束范围等；
- `applicability_conditions`：什么情况下适用；
- `contraindications`：什么情况下禁止使用；
- `source_episode_ptrs`：支撑这条抽象经验的原始 episode 指针；
- `environment/provenance`：语料、索引、检索器、执行器版本；
- 独立目标题上的 benefit、harm、coverage 与时间衰减统计。

RRM 已经存储 task type、applicability conditions、required evidence、retrieval strategy、undesirable behaviors 和 query-adjustment patterns，并将经验只转成 query-level guidance；因此“增加适用条件”本身不是创新。GrowRAG 需要进一步研究这些条件能否被定量校准，以及怎样控制 `DIRECT 原本正确 -> REUSE 后错误`。

一手来源：https://arxiv.org/html/2607.28156

另外，OpsMem 已在微服务故障诊断中明确采用“当前事件 STM + 跨事件 LTM + state-aware activation + 解决后 consolidation”。它不是文本 RAG，但说明“短期状态 + 长期经验”这个高层结构本身也不能作为新贡献。

边界来源：https://arxiv.org/abs/2607.11357

## 3. 局部 episode 如何晋升为长期经验

不采用“每题结束就让 LLM 覆盖总结”的方式。

建议流程：

1. 当前任务结束，冻结原始 episode；
2. 只有某次修复相对原查询产生配对增益，才生成 candidate card；
3. candidate card 保留对原始 episode 的指针，不能覆盖或删除原证据；
4. 在独立问题上验证迁移收益和伤害；
5. 多个相似 candidate 可以形成新的 abstraction，但旧卡和原 episode 保留版本；
6. 只有跨问题证据足够，才晋升为 active global memory；
7. 退化后进入 cold/quarantine，而不是无痕删除。

这使“原始轨迹”和“抽象经验”形成可回溯关系，直接吸收 Useful Memories 的主要警告。

## 4. S2G 风格结构化失败状态

S2G-RAG 在每轮读取原问题 `q` 与累计证据 `Ct`，输出：

```text
sufficient: true / false
gap_items:
  - category: bridge_entity | attribute | relation | evidence_span | other
    target: 当前缺失信息围绕的实体
    slot: 缺失的属性或关系
    description: 简短说明
```

如果充分，则回答；如果不足，则把 gap item 映射为下一条查询。S2G 的局部 Evidence Context 是句子级的，减少多轮检索的噪声累积。

一手来源：https://aclanthology.org/2026.acl-long.1185/

GrowRAG 可以扩展为：

```text
failure_state:
  sufficient: false
  failure_mode: missing_relation
  gaps:
    - category: relation
      target: Chris Columbus
      slot: country_of_birth
      description: 已找到导演身份，但缺少其出生国家
  progress:
    new_support_coverage: 0.5
    evidence_novelty: 0.3
    redundancy: 0.6
  next_action: REUSE_REPAIR | FRESH_REPAIR
```

关键区别：S2G 的 gap 描述当前题缺什么；GrowRAG 的长期经验卡描述历史上这种 gap 曾怎样被修复、在什么条件下可靠。

还要注意：S2G-Judge 不是一个未经训练的 prompt 小组件。论文使用执行轨迹构造 `(q, Ct)` 状态，由教师标注，再对小模型进行 LoRA；它的停止条件是 `sufficient=true` 或达到最大轮数，并没有边际增益停止。因此如果首版使用冻结 LLM 输出同样 schema，只能称为轻量替代实现，不能声称复现了 S2G-Judge。

结构化状态还必须标记阶段：

- `stage=pre`：检索前只能描述预计查询缺陷，如实体歧义、组合关系或缺少约束；
- `stage=post`：检索后才能描述实际证据缺口，如缺桥接实体、属性、关系、矛盾或无新增证据。

不能把检索前预测的风险写成已经观察到的 evidence gap。

## 5. 完整控制流程候选

```text
问题 q0
  -> 检索前：DIRECT 或可信的 PROACTIVE_REUSE
  -> 首次检索
  -> 建立局部 Evidence Context
  -> 判断充分性 + 显式 gap + 本轮进展
       -> sufficient                         : ANSWER
       -> insufficient + 有可信适用经验      : REUSE_REPAIR
       -> insufficient + 无可信适用经验      : FRESH_REPAIR
       -> 无进展或预算耗尽                   : STOP_ABSTAIN
  -> 下一轮检索
  -> 问题结束后冻结 episode，离线判断是否产生 candidate card
```

这会把检索前主线与检索后闭环连接起来，但也明显扩大首篇论文范围。

## 6. 停止搜索不能只看一个条件

ReflectiveRAG 同时描述了：

- SLM 输出 `Sufficient / Refine`；
- 基于相邻检索结果稳定性与置信变化的 marginal-improvement 阈值；
- 论文算法主体仍以 `Sufficient` 作为循环结束条件。

一手来源：https://aclanthology.org/2026.eacl-industry.27/

因此不能简单把论文中的一个公式直接当成可靠停止保证。建议 GrowRAG 把停止拆成三道门：

论文当前还存在可复现性缺口：公开正文没有把 `Sim`、`Conf`、权重与停止阈值完整操作化，Algorithm 1 仍只写 `until Sufficient`。所以它适合作为思想与方法基线，不适合直接把边际公式复制成我们的“可靠停止器”。

1. **充分停止**：现有证据已经逐项支撑原问题；
2. **无进展停止**：新证据覆盖、文档新颖度和答案置信均没有实质改善；
3. **预算停止**：达到最大轮数、检索次数、token 或延迟预算。

在第 2/3 类停止时，如果证据仍不足，应 `ABSTAIN` 或返回“证据不足”，而不是假装已经 sufficient。

第一版不要把多个量立即压成一个不可解释总分。先分别记录并画出准确率、停止轮数和成本的 Pareto 曲线，再决定是否学习一个 stopping controller。

2026-08-13 的预印本《When Should Multi-Round RAG Stop?》已经把 S2G-style judge 接到 Search-R1 stopping，并强调部署由轨迹上的第一次 STOP 决定：一次过早停止会截断所有后续状态，减少检索次数也不等于安全或总成本更低。因此若以后主攻停止，不能只做“S2G judge + 阈值”，而应专门评价 premature-stop harm、风险—覆盖率和 judge 自身成本。

边界来源：https://arxiv.org/abs/2608.13237

## 7. 三个可选研究范围

### 方案 A：保持当前首篇论文最小范围（推荐）

- 主方法仍是检索前可信复用；
- 双层记忆只作为数据组织原则：保留 raw episode，长期卡不覆盖更新；
- S2G/ReflectiveRAG 作为 fresh-repair 强基线；
- 暂不训练 sufficiency judge。

优点：最容易起步、归因最清楚。
风险：方法看起来不像完整 Agent 闭环。

### 方案 B：可信复用 + 结构化 fresh fallback

- 检索前尝试可信复用；
- 首检不足时输出 S2G-style gap；
- 先寻找匹配的历史 gap->repair，找不到再 fresh repair；
- 用充分性、无进展和预算共同停止。

优点：形成可靠修复闭环，与用户偏好最一致。
风险：与 RRM、ReflectiveRAG、S2G 的组合非常接近，必须把创新集中在可校准适用性、反事实伤害和 raw-to-abstract provenance。

### 方案 C：把“安全停止”作为主要研究问题

- 不主打新记忆结构；
- 主问题变为：在历史经验介入的多轮检索中，什么时候继续、重试、放弃或回答；
- 重点评价 premature stop、over-retrieval、原本正确后被破坏和总成本。

优点：问题明确，可能比再造记忆结构更有新颖性。
风险：需要高质量的 turn-level sufficiency 标签或可靠代理信号。

## 8. 尚待用户决定

1. 局部记忆是否命名为“单文档记忆”，还是更通用的“当前任务局部记忆”？建议后者。
2. 首篇论文是否仍坚持纯检索前路线 A，还是接受方案 B 的范围扩张？
3. S2G-style judge 首版采用冻结 LLM prompt，还是训练小模型？建议先冻结 LLM 验证现象。
4. 长期记忆是否只允许经过独立问题验证的成功修复，还是另外建立失败诊断库？建议首版服务侧只用成功修复，失败记录仅供审计。
5. 停止条件是先采用可解释的三门规则，还是直接学习 controller？建议先规则和完整日志，后续再训练。

## 9. 当前最有希望的中心问题

在已核对的 Useful Memories、RRM、ReflectiveRAG、S2G-RAG、OpsMem 和 stopping 近邻范围内，最值得继续验证的不是“双层记忆”本身，而是：

> 局部具体的检索修复，能否在保留原始 episode 和来源指针的前提下，安全晋升为跨任务的去实体化修复经验；调用时能否分别校准历史可靠性、当前适用性以及正确到错误的复用伤害？

对应的支撑贡献是：

1. `episode-backed promotion`：抽象卡永远能回溯原始 episode，且一次成功不能直接 active；
2. `structured applicability`：当前 query/gap state 与适用条件、禁用条件显式匹配；
3. `harm-aware abstention`：不确定时保持 DIRECT 或 fresh repair，并报告 risk–coverage；
4. `observable stopping`：充分、无进展、预算耗尽分别记录，绝不把“搜不动了”伪装成“证据充分”。

这仍然是搜索范围内的暂定空隙，不是对全领域“绝对首次”的保证。
