# 查询侧可信复用层 v1：易懂且可执行的技术方案

更新日期：2026-08-19
状态：第一版实施方案

## 1. 它到底放在哪里

普通 RAG：

```text
用户问题 → 检索 → 文档 → 生成答案
```

GrowRAG v1：

```text
                         ┌─ DIRECT：保持原问题
用户问题 → 查询侧可信门 ┤
                         └─ REUSE：使用历史查询变换生成的候选查询
                                  ↓
                              同一个检索器 → 文档 → 同一个生成器
```

它是索引外的 sidecar：关闭它以后，系统必须严格退化成原始 RAG。

## 2. 我们记住什么

不是历史答案，也不是历史检索文档全文，而是一张**查询变换经验卡**：

```text
来源问题 q_s
原检索查询 q_s^0
成功查询 q_s'
原子变化：增加了什么、删除了什么、怎样分解或消歧
变换类型：消歧 / 补关系 / 多跳分解 / 时间限制……
来源上的 DIRECT 与变换结果
语料、检索器、索引和生成方法版本
后来在独立问题上的 benefit / harm 记录
当前状态：candidate / active / quarantine / retired
```

例如：

```text
来源问题：
  Which film director was born first, A or B?

原查询：
  Which film director was born first, A or B?

成功变换：
  A birth date
  B birth date

原子变化：
  把“谁更早出生”拆成两个实体属性查询，再比较日期。
```

重点不是把“A birth date”原封不动复制到另一题，而是保存这个变换的来源和结构。真正应用到当前问题时，必须得到针对当前实体的新 query variant。

## 3. 为什么把“应用变换”和“选择变换”分开

历史经验迁移包含两个不同问题：

1. **Application**：如何把历史 `q_s → q_s'` 应用到当前问题 `q_t`，产生 `q_t'`；
2. **Selection**：产生的 `q_t'` 是否值得替代 `q_t`。

如果让同一个 LLM同时生成、选择并评价，就很难知道收益来自哪里，也容易循环自证。

因此 Gate 1 采用最干净的接口：

```text
当前问题 + 历史经验
    ↓ 固定的候选生成方式
一个明确的当前题 query variant
    ↓ GrowRAG 只判断是否采用
DIRECT 或 REUSE
```

第一阶段可以离线预生成候选；后面再比较三种 application：

- 固定 prompt，把来源 pair 当一个 few-shot 示例；
- ReFormeR 风格 typed pattern；
- 可参数化的确定性模板。

每种方式都单独记录成本。若 REUSE 仍调用同等规模 LLM，就不能虚报“节省反思成本”。

## 4. 三种“成功”必须分开

### 4.1 来源成功 source-valid

查询变换在产生它的来源题上，相对 DIRECT 有明确净增益：

``
\Delta_{\text{source}} = U(q_s') - U(q_s) > \delta_{\text{write}}
``

只有通过这个门才进入 `candidate`。

### 4.2 历史可靠 historical reliability

它在多个**独立目标题**上复用后：

- 平均净增益不为负；
- benefit 次数足够；
- harm 次数和**条件破坏率**的置信上界足够低；
- 观测数量达到最低要求。

这决定经验本身是否从 `candidate` 晋升为 `active`。

### 4.3 当前适用 current applicability

即使一条经验历史可靠，也可能不适合当前题。适用性只回答：

> 当前问题和这条经验的结构、语义条件及运行环境是否匹配？

第一版可见特征：

- 当前 query 与来源 query 的词汇/语义相似度；
- 问题类型或变换类型是否匹配；
- 实体数、关系词、时间条件等结构特征；
- corpus/retriever/index 版本；
- 经验年龄只作为辅助，不代替语义匹配。

目标题的 gold、执行后的检索结果和最终答案不能进入纯检索前适用性特征。

## 5. 检索前决策顺序

对当前问题 `q_t`：

### 第一步：召回候选经验

从历史库召回 top-m 来源问题相似的经验。m 必须固定并报告，因为候选越多，oracle 越容易“碰巧选中”。

### 第二步：硬失效检查

以下任一情况直接拒绝：

- 状态不是 `active`；
- corpus/retriever/index 版本不兼容；
- 经验被 quarantine 或 retired；
- provenance 缺失；
- 当前候选查询为空或违反预算。

### 第三步：历史可靠度门

分别检查：

- 独立迁移观测数；
- 平均成对增益；
- harm rate；
- harm 的 Wilson 95% 置信上界。

这里特别区分两个比例：

- 整体 harm rate：全部尝试里有多少次把结果改坏；
- 条件破坏率：在 DIRECT 原本正确的题里，有多少次被 REUSE 改错，即
  `HARM / (HARM + BOTH_GOOD)`。

第二个比例更直接对应“不要破坏原本正确查询”。Wilson 上界的作用是：一次成功不能让一条经验显得“100%可靠”；如果还从未遇到 DIRECT 原本正确的独立题，也不能声称已经证明它安全。

### 第四步：当前适用性门

适用性低于在 dev/calibration 集冻结的阈值时拒绝。

### 第五步：选择或旁路

- 没有经验同时通过两个门：`DIRECT`；
- 有一个或多个通过：按适用性优先、历史风险次优的明确规则选一个 `REUSE`；
- 完整记录所有接受/拒绝原因。

## 6. 多级经验队列

```text
candidate
  来源题有净增益，只能 shadow 验证
      ↓ 独立问题上证据充分
active
  可以参与线上候选召回，但仍需当前适用性门
      ↓ 出现高风险伤害或漂移
quarantine
  暂停自动复用，只保留审计与重新验证
      ↓ 明确不可兼容或长期失效
retired
  不再召回，但不删除历史记录
```

EMA 以后可以平滑近期增益或帮助发现漂移，但不参与 v1 的“是否适合当前题”证明。

## 7. 第一版评价

同一道题必须执行相同预算的 `DIRECT` 和 `REUSE`：

| DIRECT | REUSE | 标签 | 含义 |
|---|---|---|---|
| 错 | 对 | benefit | 历史经验修好了问题 |
| 对 | 错 | harm | 历史经验把正确问题改坏 |
| 对 | 对 | both-good | 复用可能多余，比较成本 |
| 错 | 错 | both-bad | 经验没有修复 |

主结果同时报告：

- 答案 EM/F1；
- supporting document/fact Recall；
- benefit rate；
- harm rate；
- reuse coverage；
- selective risk；
- risk–coverage curve；
- retrieval/LLM 调用、token 和延迟；
- full-memory oracle、candidate-set oracle 和实际 gate 的差距。

## 8. Oracle 在本项目中的位置

Oracle 不是系统组件，而是离线诊断上界。

对一题的所有候选都执行后，事后看 gold：

- **reuse oracle**：历史候选中最好的一条；
- **policy oracle**：DIRECT、所有 REUSE 和 FRESH 中最好的一条；
- **candidate-set oracle**：只在真实召回的 top-m 里选；
- **full-memory oracle**：在整个历史库里选。

full-memory → candidate-set 的差距表示经验召回瓶颈；candidate-set → 实际 gate 的差距表示决策瓶颈。

如果 oracle 都没有明显收益，项目必须止损，不能靠训练一个 gate 把不存在的信号“学出来”。

## 9. v1 代码模块

```text
src/growrag/
├── config.py                 # 严格 TOML 配置与运行前 fail-closed
├── pipeline.py               # 完整查询侧 facade
├── runtime_io.py             # request / plan / decision 文件协议
├── models.py                 # query transformation 与环境指纹
├── experience/
│   ├── ledger.py             # candidate/active/quarantine/retired
│   └── snapshot.py           # 可重启、严格校验的 JSON 经验快照
├── selection/
│   ├── applicability.py      # 当前 query–experience 匹配
│   ├── candidates.py         # 独立的历史候选召回与固定 top-m
│   └── gate.py               # 硬失效、双门与 DIRECT/REUSE
├── rewrite/
│   └── application.py        # 来源经验 → 当前题 query plan
└── evaluation/
    ├── paired.py             # 四格成对标签
    └── oracle.py             # Gate 1 上界与止损统计
```

外部检索器、LLM、数据加载器都通过接口接入，不进入第一批核心逻辑。

## 10. 第一阶段不做什么

- 不下载和索引完整 MS MARCO；
- 不训练 dense retriever；
- 不训练 LLM rewriter；
- 不实现 bandit/RL；
- 不加入图记忆；
- 不加入答案缓存；
- 不把历史文档直接放进当前上下文；
- 不先追求漂亮的端到端数字。

第一阶段只证明：定义、账本、决策和 oracle 评价是否严谨且可运行。
