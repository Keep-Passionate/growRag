# S2G-RAG：原文核验、训练规模与成本审计

> 最需要掌握：S2G 不是“让模型再改写一次”，而是让控制器先输出“够不够回答、还缺什么”，再用确定规则拼检索词。它适合作为不使用跨题经验的强 FRESH 对照。完整主方法训练了一个 3B 判断器；论文还单独测试了不训练的教师控制器变体，不能把两者混称为同一个复现。

核验日期：2026-09-24。以下区分**作者报告、代码核验、我们的分析、估算**。本轮未执行模型、未调用付费 API、未租 GPU。此文是中文导读和审计，不是官方译文，不替代原论文。

## 2. 原方法到底执行什么

```text
原问题 q + 累计证据 C
          ↓
判断器：是否充分？如果不充分，缺什么？
          ├─ 充分 → 答案模型回答
          ├─ 检索预算已满 → 仍由答案模型给出最终答案
          └─ 不充分且还有预算
                    ↓
          缺口字段 → 确定性拼接检索查询
                    ↓
          检索 → 选择原文句子 → 追加到累计证据 C → 回到判断器
```

原文 §3、附录 C 的关键细节：

- Judge 输入是原问题和累计证据，不是历史题库，也不需要先生成一个草稿答案再评判。
- 输出包含 `sufficient` 和 `gap_items`。每个 gap 包含 `category / target / slot / description`：缺口类别、对象、属性或关系位置、补充描述。
- 类别包括桥接实体、属性、关系、证据片段等。这里的“结构”是本题检索缺口，不是跨题经验卡。
- Query builder 将原问题与选定 gap 的 `target + slot` 拼接；必要时用描述回退。不是又调用一次 LLM 把完整问题自由改写。
- Extractor 输出原文句子编号，再由程序取回原句及标题，尽量避免重新写摘要产生事实变化。累计证据是这些原文证据块的追加，不是完整历史推理过程。
- 主实验最多 4 次检索，每轮取 6 篇候选文档。预算用完仍回答；论文没有把“始终不回答”作为避错方案，也没有实现完善的拒答机制。
- 算法 1 的最坏调用上界是 5 次 Judge、4 次 Extractor、1 次最终回答，加 4 次检索。模型调用的数量不等于付费 HTTP 请求数量：可能本地批处理，也可能 API。

**重要纠正：**附录 A.2 的正式默认值是每轮使用 `K=1` 个 gap；作者代码的 HotpotQA 默认使用最多 3 个。比较实验必须明确按论文还是按仓库默认配置，不能静默混用。[查询构建代码](https://github.com/nianaaa/S2G-RAG/blob/5d842a67a0a99a7b545bbad0dc402ceaae0e5eff/inference/inference_bm25.py#L326)

## 4. 混淆矩阵审计：6.44% 的分母不能弄错

位置：§4.5.2、Figure 2，PDF 7 / 25852。图注明四个格子均占**整个评价集合**的百分比：

| 实际代理标签 \ 预测 | 不充分 | 充分 |
|---|---:|---:|
| 不充分 | 48.27% | 6.44% |
| 充分 | 31.60% | 13.70% |

作者正文把 6.44% 称为 false-positive rate；按该图的分母，6.44% 实际是 `FP / 全部样本`。通常的条件误报率应为：

```text
FPR = FP / (FP + TN) = 6.44 / (6.44 + 48.27) ≈ 11.77%
预测“充分”的精确率 = TP / (TP + FP) = 13.70 / (13.70 + 6.44) ≈ 68.02%
充分状态的漏报率 = FN / (TP + FN) = 31.60 / (13.70 + 31.60) ≈ 69.76%
```

更重要的是，图中的“实际”不是人工判定压缩后证据语义是否足以回答，而是：**累计检索标题是否覆盖全部 gold supporting document titles**。这只是文档覆盖代理标签。

所以不能把 68.02% 直接叫作语义充分性的真实准确率，也不能把检索到支持文档等同于选中的句子已经支持答案。这个区分恰好帮助我们拆开检索、证据提取和充分性判断三个错误来源。以上是我们的指标审计，不是作者另行报告的实验。

## 5. 训练集怎样生成，规模究竟多大

来源：附录 B，PDF 12–14 / 25857–25859；[生成脚本](https://github.com/nianaaa/S2G-RAG/blob/5d842a67a0a99a7b545bbad0dc402ceaae0e5eff/generation/generation.py)、[教师标注](https://github.com/nianaaa/S2G-RAG/blob/5d842a67a0a99a7b545bbad0dc402ceaae0e5eff/training/label_with_teacher.py)、[训练脚本](https://github.com/nianaaa/S2G-RAG/blob/5d842a67a0a99a7b545bbad0dc402ceaae0e5eff/training/train_s2g_judge_lora.py)。

1. 用未微调的 Judge 收集真实检索轨迹，固定走最多 4 轮，而不是只收集理想证据。
2. 每个问题在每轮形成一个 `(问题, 当前证据)` 快照。快照不是独立的新问题。
3. GPT-4o-mini 对快照给出充分性和结构化缺口标签。提示要求只能根据当前证据。
4. 检查 JSON 格式，用 gold 支持页信息作弱校验，丢弃明显冲突的监督记录。gold 不作为 Judge 输入。
5. 清洗后 2,804 个快照，其中充分 1,396、不充分 1,408；各轮为 764 / 739 / 653 / 648。
6. 快照随机 90/10 划分，seed 42：训练 2,523、验证 281。不是用整个 HotpotQA 训练集逐题训练一遍。

**没有公布的量：**原始标注快照总数、清洗保留率、独立问题总数、各数据集贡献的快照数、训练墙钟时间。不能用 `2804÷4` 当作独立问题数。

**我们的验证改进建议：**同一问题的不同轮次可能高度相关。代码按行随机划分，不保证同一问题的全部轮次落入同一集合；这构成泄漏风险，而不是我们已证实发生了多少泄漏。我们应按 question ID 分组划分，并保留独立测试问题。[训练划分代码](https://github.com/nianaaa/S2G-RAG/blob/5d842a67a0a99a7b545bbad0dc402ceaae0e5eff/training/train_s2g_judge_lora.py)

## 6. 可审计的费用估算：不把猜测当实测

### 6.1 教师标注 API

2026-09-24 核验的 GPT-4o-mini 普通文本价格：输入 $0.15 / 百万 token，输出 $0.60 / 百万 token；未使用缓存或 Batch 折扣。[官方模型页](https://developers.openai.com/api/docs/models/gpt-4o-mini)

设 `p` 为标注清洗保留率，`a` 为重试带来的付费 token 倍数，`I/O` 为每次平均输入/输出 token：

```text
N_raw = ceil(2804 / p)
教师费用（美元）≈ a × N_raw × (0.15 × I + 0.60 × O) / 1,000,000
```

| 假设保留率 | 原始标注次数 | I=1500、O=200、无重试 | I=3000、O=300、无重试 |
|---|---:|---:|---:|
| 100% | 2,804 | $0.97 | $1.77 |
| 70% | 4,006 | $1.38 | $2.52 |
| 50% | 5,608 | $1.93 | $3.53 |

**这些是代入假设后的算术，不是作者账单，也不是我们的报价。**不含生成原始轨迹、验证/测试、失败请求、额外重试、本地 GPU 费用。原代码标注输出上限为 512 token，但不代表实际每次都生成 512；输入也不能用 SFT 截断长度替代实测 API 输入。

生成轨迹时，每题固定 4 次未训练 Judge、4 次证据提取、1 次最终回答。若后两者走 API，还要单算其 token；如果都本地跑，则计入 GPU 时。需要先记录 20–50 题的真实 token、清洗率和耗时，才能给出可靠预算。

### 6.2 3B LoRA 的 GPU 时

训练样本呈现次数为 `2523 × 3 = 7569`。设 `L` 为实际有效的平均计算长度（包括 padding 影响），总训练 token 工作量近似为 `7569 × L`：

| L | 三轮总 token 工作量 |
|---:|---:|
| 512 | 3,875,328 |
| 1,024 | 7,750,656 |
| 2,048 | 15,501,312 |

以单卡执行为例，若短测得到实际吞吐 `S`，且额外开销比例为 `h`：

```text
训练墙钟小时 ≈ 7569 × L / S / 3600 × (1+h)
GPU 卡时 = GPU 卡数 × 墙钟小时
租赁费用 = GPU 卡时 × 每卡每小时单价
```

例如只作敏感性分析，`L=1024、h=20%`，如果实测 S 分别为 200 / 500 / 1000 token/s，则约为 12.92 / 5.17 / 2.58 小时。**这三个 S 是假设，不对应任何承诺的 3090、4090 或 A100 实测速度。**长度 2048 时上述 token 近似量翻倍。训练、验证、保存、加载、检索生成轨迹应分开计时。

作者单卡默认微批 2、累积 8 对应有效批约 16；每 epoch 约 1,262 个 microstep、158 个更新 step，三轮约 474 次更新，最终以训练器日志为准。也可先测每次 optimizer step 秒数，用 `474 × 秒数 / 3600` 估计。

实用建议（我们的工程判断，未实测）：先用单张 48GB 卡做 3B LoRA 的短测较省排障；24GB 卡可尝试更小微批、梯度检查点，但不能未测就保证照搬作者默认参数能装下。8GB 笔记本不是本次忠实重跑首选。单独训练 3B 和同时运行 3B Judge、8B 提取/回答器是不同资源问题。

## 7. 代码与论文之间必须记录的差别

| 项目 | 静态审计发现 | 我们应怎样处理 |
|---|---|---|
| gap 数 | 论文默认 K=1；仓库 Hotpot 默认最多 3 | 显式参数化，首先按论文 K=1；另报告仓库默认敏感性 |

## 8. 从作者局限到 GrowRAG：哪些方向值得试

下表是**我们的推断及待检验假设**，不是“已经证明空白”，也不是 S2G 作者声称的未来成果。

| 切口 | 为什么与原文有关 | 最小验证 | 不能怎样包装 |
|---|---|---|---|
| 充分性校准与分层归因 | 文档覆盖、句子支持、答案正确并不相同 | 固定检索轨迹，分别标出支持文档是否到达、句子是否保留、Judge 是否识别 | 不能把增加一个可靠性分数就叫新方法 |
| 可复用的失败状态—动作对应 | S2G 逐题解决当前缺口，不维护跨题程序经验 | 固定强 FRESH，比较历史动作是否带来它达不到的增量；报告有益/有害复用与调用成本 | 不能把历史答案直接塞给回答器充当经验收益 |
| 少量依赖结构而非更长卡片 | 作者指出多实体、时间和关系组合超出平面字段 | 同样候选和预算，比较平面 gap 与带前置依赖的动作表示 | 作者已提丰富结构，不能声称此前无人想到 |
| 防止证据压缩切断关系 | 作者承认跨句与消歧上下文会被遗漏 | 原句指针、固定邻句、自适应邻句三种控制，固定 token 上限 | 原提示已经要求最小必要上下文，不能只换一句提示词冒充新意 |
| 耗尽预算后的安全退出 | Table 12 展示 Judge 一直不充分但预算耗尽后仍给错答案 | 固定覆盖率下比较强制回答、可解释部分回答/拒答及成本 | 不能靠永远拒答获得低错误率 |

对我们最相关的研究问题可以暂写为：**在同样的有界 FRESH 控制器和检索底座上，哪些历史“状态—动作—适用条件”记录能提供可迁移的额外证据收益，而不会增加原本可答问题的损害？**这仍是需要实验收窄的问题，不是已获证明的创新结论。

## 9. 下一步建议：先验证基线本身，再谈改进

1. 固定模型、检索语料、K=1、T=4 和答案评分；先在 10–20 题检查每轮 JSON、查询构建、原句指针、强制停止与成本日志。
2. 先跑作者的教师控制器变体或明确命名的同构 API 适配，避开“没训好 Judge 导致基线过弱”。若模型替换，注明不是原数值复现。
3. 在独立开发子集上报告 BASE、强 FRESH 的逐题配对结果；检查错误到底出在检索、句子提取还是 Judge，不能只看总 F1。
4. 如控制器效果和成本可接受，再采集训练问题的真实轨迹、教师标注、按 question ID 分组训练/验证，进行 3B LoRA。训练问题不得进入正式测试。
5. 最后加跨题经验。保持候选数量、最大检索轮数、提示长度尽可能可比，单独测量 `MEMORY − FRESH`，不要把额外轮数全部算给记忆。
