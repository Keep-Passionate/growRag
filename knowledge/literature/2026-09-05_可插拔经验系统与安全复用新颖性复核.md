# 可插拔经验系统与查询修复安全复用：新颖性复核

核对日期：2026-09-05。性质：独立批判性研究备忘，供本轮路线收敛；不是已获实验支持的论文贡献声明。已只读检查 `CURRENT_PROJECT_MEMORY.md`、08-24 累计证据方法稿及 `selection/gate.py`、`experience/ledger.py`；未改运行代码。

本次以论文原文、ACL Anthology、PMLR 和作者代码库为依据；旧项目笔记只用于定位需要核对的主张。新论文的“未见”均限定于本次查阅的方法与实验，不能外推为所有相关工作都没做。

## 1. 需要先纠正的判断

1. **可插拔经验记忆系统已存在。** 可插拔、冻结底座、query-only reuse、经验适用条件、成功后写入、衰减与淘汰均不能成为 GrowRAG 的独立新颖性主张。
2. **其他系统也做可靠性与支持判断。** RRM、ReMe、ERM、GAM-RAG、LivingRAG 都已有相关机制。问题是各自判断的对象和证据强度不同，不能把前人描写成“成功就永远相信”。
3. **“原来正确、用了记忆以后错误”的统计分解也已有直接先行工作。** `When Continual Learning Moves to Memory` 明确区分 baseline-success 与 baseline-fail 子集，并报告 Retention Rate / New Learning；不能把同类指标重新命名作为核心创新。
4. 08-24 的方案仍有研究价值，但需要把主张从“架构新颖且安全”收缩为可证伪问题：**对于同一检索缺口，历史修复在什么条件下优于现场修复？能否用执行前可见信息选出这些情况，并在固定预算与回答覆盖率下减少有害复用？**
5. `safe` 目前是研究目标，不是现有代码已获得的安全保证。已有门控和审计接口只能说明工程上准备测量/限制风险。

## 2. “不改 RAG”有三种不同意思

| 说法 | 精确定义 | GrowRAG 适合怎样表述 |
|---|---|---|
| 冻结模型参数 | 不训练 retriever / generator 权重 | 是，但大量 prompt 和 memory 方法都满足 |
| 保留基础组件与语料索引 | 不改索引、retriever 算法、generator 权重，仍可能变更输入与调用次数 | 是，建议正式采用此表述 |
| 整体执行架构不变 | 检索调用顺序、query、context、控制流均不变 | 当前方案 B 不满足；多轮修复、Judge、路由已经扩展工作流 |

因此可以说“可接到现有检索器和回答模型上的查询控制层”，但不宜说“整个 RAG 架构完全没改变”。它是否真正可替换，要用至少第二种检索器/底座检验，不能只依赖接口命名。

## 3. 最直接近邻与边界

### 3.1 RRM：必须逐段对照的近邻

[RRM 原文](https://arxiv.org/html/2607.28156v1) 的 Reflective Retrieval Control 已包括：本题 question、query history 和 evidence 驱动的 Online Query Reflection；同一异常触发条件下选择跨题经验；依据 applicability conditions、required evidence 和 failure modes 判断适用；成功经验优先，失败经验采用更严格条件。经验指导 query，回答仍仅使用当前视频重新取得的事实证据。生命周期依据实际执行后的新证据、使用反馈与时间衰减更新，并合并、裁剪和保护冷启动条目。

对应 GrowRAG：FRESH / REUSE、query-only、当前适用性和生命周期均有直接重合。文字多跳 QA、独立 source/test、真实 BASE/FRESH/REUSE 结果对照可形成研究设定差异，但只把视频换为文字不足以成为强方法贡献。

RRM 也保留了相同事实记忆与检索设施，不能把它简单归类为“必须替换整个底座”。另一方面，它依赖多模态图记忆与原有 Search–Answer 状态，不是任意字符串检索接口的即插即用实现。

### 3.2 ReFormeR：查询模式复用的直接基线

[ReFormeR 原文](https://arxiv.org/html/2604.01417v1) 从原 query 与实测更强改写的配对中提炼模式，结合当前检索结果选模式，再实施受控改写，目标之一就是减少 query drift。它从 MS MARCO train 来源的 Diamond 子集抽取 10,000 对，用 TREC DL 2019/2020 与 DL Hard 检验。

这已覆盖“成功改写 → 抽象经验卡 → 当前上下文选卡 → 定向改写”。它侧重 IR query reformulation；GrowRAG 若保留多跳证据状态，应证明 gap / 历史成效信息比 ReFormeR 的文档上下文选择带来新增预测价值。[作者代码](https://github.com/aminbigdeli/ReFormeR) 可作复现参考。

### 3.3 ReMe：可靠性与适用性不是我们才开始区分

[ReMe，Findings of ACL 2026](https://aclanthology.org/2026.findings-acl.829/) 使用程序经验、场景感知索引、针对当前情境的适配，以及基于效用的加入与清理。成功/失败及比较经验均被考虑。[原文](https://arxiv.org/html/2512.10696v2) 应用于 BFCL-V3、AppWorld 等 Agent 任务。

它主要是通用程序记忆而非文档 QA 查询修复，但已足以反驳“历史质量和当前适用的分工是全新思想”。GrowRAG 必须说明如何估计增量收益、如何避免当前查询误用，以及这些机制相对 ReMe-style reuse 是否有效。

### 3.4 LivingRAG：上轮之后新增的直接经验 RAG

[LivingRAG](https://arxiv.org/html/2608.25960v1) 首发 2026-08-26。它保持 LinearRAG 的语料图和图排序过程，新增经验库，存查询表示、稀疏图激活、紧凑推理 scaffold 与验证信息；复用时改变初始实体激活并辅助回答。写入门是证据 grounding 加 novelty，grounding 使用 NLI。论文明确：grounding score 反映证据支持，**不直接判断未来问题上的效用**。

这与 GrowRAG 的共享点是“在已有 RAG 上加经验，并选择性写入”；差异是它改变图激活与生成上下文，而 GrowRAG 希望约束在 query 操作。它的在线顺序评测不等同于我们拟做的固定库迁移测试。本次未见对部署新问题上的条件伤害率作保证；不能据此把其已有支持和筛选机制忽略。

### 3.5 ERM 与 GAM-RAG：都是训练自由，但不是同一种查询旁路

[ERM](https://arxiv.org/html/2602.05152v1) 通过 correctness-gated feedback、选择性 attribution 与有界渐进更新，把查询扩展信号写进文档 key / 检索索引。其 verifier 可用检索或生成成功信号，且两者任一成立即可通过。它明确追求稳定记忆更新。因此“正确后持久化、避免漂移”不是 GrowRAG 独有；**不修改索引**是接口差别，而不是自动成立的性能优势。

[GAM-RAG](https://arxiv.org/html/2603.01783v1) 为句子维护 task / time 记忆向量与不确定性，利用 LLM 判断句子证据价值，再以 Kalman-inspired gain 更新；检索组织与激活会随记忆改变。它的 reliability 对象主要是句子记忆和更新信号，GrowRAG 的对象是查询操作在新问题上的相对效果。这是可解释的对象差异，仍需实验，不能因把概率名称分成两个就宣称更安全。

2026-09-06 补正：其 Table 2 / 附 D 已包含 2Wiki 同题、同义题和独立同型新题评价，不能把“测试新问题”列为它没做过。具体拆分见数据总表。本轮还发现 RAG 相对收益预测已有 [ECIR 2026 正式工作](https://link.springer.com/chapter/10.1007/978-3-032-21289-4_24) 和 [Dado 等最新 v3](https://arxiv.org/abs/2604.07985v3)；“预测相对收益”概念也不是 GrowRAG 的创新。

### 3.6 C-3PO、SPARKLE、Experience-RAG Skill、MemCon、ERSkill

| 工作 | 已经做到什么 | 对 GrowRAG 的限制 |
|---|---|---|
| [C-3PO，ICML 2025](https://proceedings.mlr.press/v267/chen25an.html) | 保留 retriever 与 LLM，额外小代理控制检索、query 和信息筛选 | 冻结底座上的控制层已是正式顶会工作；它不主要依赖跨题外部经验库 |
| [SPARKLE，ACL 2026](https://aclanthology.org/2026.acl-long.1793/) | 独立 proxy、结构化检索策略、RL 与跨底座迁移 | Agentic / 结构化 / 可插拔本身不是创新 |
| [Experience-RAG Skill](https://arxiv.org/html/2605.03989v1) | Agent 与 retriever pool 之间的显式经验策略路由层 | 最字面相近的可插拔经验系统；当前实验规模和规则路由强于学习器，阅读优先级可低于成熟主会工作 |
| [MemCon](https://arxiv.org/html/2607.13591v1) | 包裹不同 memory backend，选择 Retrieve、计划注入、Consolidate、Forget、NoOp | “允许不用记忆”、轻量控制和生命周期动作均已有研究 |
| [ERSkill](https://arxiv.org/html/2608.12720v1) | 可执行检索 skill、路由学习、experience trie、能力与部署双集合、验证后更新 | 验证准入、保留旧方案和带结果的经验程序都已有近邻 |

ERSkill 的 `oracle-safe` 命题针对已观测验证集的 oracle coverage；实际 router 表现可暂时下降，且不推出未知测试分布上不退化。这个区分也适用于 GrowRAG：offline oracle 上看起来安全，不意味着在线门控安全。

## 4. “安全”需要拆开评价对象

| 判断 | 一个通俗问题 | 能说明什么，不能说明什么 |
|---|---|---|
| 来源成功 | 上一道题用此经验答对了吗 | 是候选来源；不能证明是经验产生了收益 |
| 内容支持 | 经验/答案中的事实有文档支撑吗 | 降低凭空事实；不能证明能转移到另一题 |
| 当前适用 | 当前条件与经验前提一致吗 | 降低明显错配；自然语言条件可能遗漏或误判 |
| 相对收益 | 同一问题用经验，比不用经验/现场修复好多少 | 直接估计效果，但需额外分支执行与独立标签 |
| 选择后风险 | 系统真正选择复用的这些问题上，有多大机会变坏 | 这是部署层研究目标；单张卡历史平均值无法直接替代 |

示例：一个历史桥接实体步骤在来源题中得到原文支持，本身完全正确。但新问题要求“最近一任”而经验模式忽略时间约束，改写可能检索到旧任者。来源成功、历史统计良好、局部文档 supported 都可以同时成立，新问题仍错。这个现象不是我们首次发现；值得研究的是一个廉价选择器能否识别并避免它。

建议用户可理解的描述为：**尽量不把原本能答对的问题改坏；没有把握时允许不用历史经验。** 论文中须进一步限定目标人群、质量度量、比较对象、预算、拒答规则和置信区间。

## 5. 直接挑战“配对伤害指标就是贡献”

[When Continual Learning Moves to Memory](https://arxiv.org/html/2604.27003v1) §2.3 将问题按 no-memory baseline 是否成功分组；RR 是已成功题引入记忆后仍成功的比例，NL 是原失败题引入记忆后成功的比例。文中直接讨论 harmful reuse 与 ineffective reuse。实验在 ALFWorld、BabyAI，以每任务阶段 200 training、100 test，并保持底座冻结。

若比较对象和二值标签相同，GrowRAG 的 `conditional_breakage = 1 - RR`、`repair_rate = NL` 是等价表达。合理贡献只能是把已有现象用于 **RAG 查询修复的选择目标、可泛化决策方法及独立评测**，不能归我们为新指标。

[Useful Memories Become Faulty](https://arxiv.org/html/2605.12978v1) 进一步表明：正确原始轨迹经过反复抽象也会产生有害记忆，原始 episodic-only baseline 很重要；双存储与选择性 consolidation 已被直接研究。需要保留这个对照，而不能预设抽象经验卡必定优于具体 `q → q'`。

本轮又核对 [08-29 更新的 v2](https://arxiv.org/html/2605.12978v2)：具体 episode 对照仍有竞争力，新增 §6.4 / 附录 L 分开检查首次压缩、旧摘要影响与原地覆盖；只追加、不覆盖仍未消除全部差距。其轨迹对照有 `Trajectory Logs (Summarized)` 表述，应称“保留具体轨迹的对照”，不笼统写成完全逐字未压缩日志。不同配置并非 Auto 一律优于 Force；不能把个别机制消融解释为所有任务中的普遍因果规律。

## 6. 当前设计的七个实质风险

### 6.1 卡级 Wilson 门可能在冷启动时几乎全部拒绝

当前代码默认风险上界 0.70、最少两条 BASE-correct 验证，只是演示参数。对零次伤害的 n 条独立观测，现有双侧 95% Wilson 上界为 `z² / (n + z²)`，`z≈1.96`。n=2 时上界约 65.8%；若要求低于 5%，至少约 73 条；低于 1%，至少约 381 条。分母还是 BASE 已正确的例子，不是总试验数。

每张细粒度卡片很难有这么多独立适用问题。建议先保留卡级历史作为特征与审计信息，在全局选择器/粗粒度动作族上做独立校准；不要把“观测不够”误说成“经验质量差”。所有区间都需要独立性/分布等前提；反复看同一校准集选卡、顺序更新、多卡筛选还会增加选择偏差。具体统计保证由另份统计方案处理。

### 6.2 现场修复才是经验的关键对照

`REUSE > BASE` 可能仅因为 REUSE 多搜了一轮。真正需要比较的是：在同一 `q0 + 累计证据 + gap` 检查点，`REUSE` 与不看历史卡的 `FRESH` 都允许一次同预算修复。若 FRESH 一样好，记忆并未带来新增价值。还应有简单的最近邻成功 query pair / ReFormeR-style pattern 对照。

### 6.3 BASE-first 会选择一个特殊人群

Judge 判不足不意味着 BASE 真答错；这里同时存在“已正确但证据被低估”和“确实缺证据”的题。只报告复杂分支 conditional harm 容易掩盖路由偏差。应同时报告全体题、Judge 判不足子集、实际接受 REUSE 子集，并在这些子集里与 BASE 和 FRESH 对照。

### 6.4 拒答不能伪装成不伤害

若系统遇到风险就不答，错误回答会减少，但有用回答也会减少。主实验先固定必须作答的 QA 评价或将拒答按错误计入总体质量；另开可拒答设置报告风险—回答覆盖率曲线。不要只在已回答问题上报低伤害，也不要混淆“经验调用比例”和“最终回答比例”。

### 6.5 Judge 可能给自己设计的目标打分

若同一 LLM 先分解 needs，又生成 query，再评价是否补齐其 needs，容易通过一个内部一致但不完整的状态。冻结 prompt 有助可复现，不能消除系统性误判。Gold answer / supporting facts 必须只在离线评估或事后反馈使用；运行时 Judge 不可看 gold。用人工复核小样本区分：need 分解错、证据抽取错、支持判断错、答案生成错。

### 6.6 “回滚”不能把正确的冲突证据自动删掉

与原证据冲突的新证据有可能更及时、更准确；不能因它来自 REUSE 就认定其污染。回滚应恢复计算分支用于比较，保留冲突的来源、版本和时间；证据处置按可信来源/时间等规则。运行过的检索、Judge 和生成成本不可因回滚从账单中抹去。

### 6.7 三层长期结构不是首轮实验前置条件

QueryEpisode 很有用，是可追溯日志。ExperienceCard 是研究对象之一。严格文档级 DocumentSession 在开放域多跳 QA 里未必能频繁复用，可能增加版本和索引负担；先保留规划与最小数据接口，等出现明确的跨题同文档收益再实现在线使用。不能为了喜欢三层而让三个模块同时承担论文核心。

## 7. 建议收缩后的路线与前置可证伪实验

暂定研究问题：**When should RAG reuse a past query repair?（RAG 什么时候该复用过去的查询修复？）**

主方法应该只承担一次决策：同一检索缺口下，选择保留原方案、FRESH，或某一条历史修复。多轮循环、证据抽取和停止采用固定基线，不同时优化。风险校准、证据契约与记忆粒度必须作为可分离候选增量，而不是提前宣布全部必要。

| 阶段 | 具体产出 | 什么结果会否定当前方向 |
|---|---|---|
| P0：固定底座和 FRESH | 能在相同题和检索前缀上重放 BASE / FRESH | FRESH 本身不稳定，或误差主要来自 generator 而非检索 |
| P1：建小型冻结经验库 | 保存成功原始 query pair，并另生成抽象卡；隔离 source 与 target | 目标题几乎找不到可迁移经验，或收益只在近重复/同答案题存在 |
| P2：离线三臂 oracle | 同状态运行 FRESH / raw-pair REUSE / card REUSE，保留全部质量与成本结果 | oracle 已无法在同成本下超过 FRESH：记忆没有可利用空间 |
| P3：简单选择基线 | 相似度阈值、全局历史效用、RRM-style applicability、QPP、以及组合 | 新特征/门控不优于廉价阈值或通用 classifier |
| P4：风险与泛化 | 固定覆盖率/预算比较 harm、repair、EM/F1，跨文档与模板复核 | 低harm完全来自不复用/拒答；跨文档后收益消失；实际总成本不划算 |
| P5：按失败类型补模块 | 仅当证据失约、漂移或稀疏反馈真实出现时，再加契约、生命周期、学习器 | 复杂模块只有结构上的美感，没有可复现增益 |

P0–P3 用官方 train 内独立划出的 source、development 组即可，保留官方 dev/test 不触碰。第一轮规模依据调用预算和卡片覆盖率选择，不应从某一论文照搬百分比。大规模完整系统应等 P2 的 oracle 空间与 P3 的可预测性同时成立。

若卡片能在相同准确率下稳定减少现场修复的生成 token / 查询次数，哪怕最高准确率提升很小，也可以形成效率论文；但用户不喜欢的 amortization 术语不必写进标题。必须计入建库和维护成本，报告达到收支持平需要多少后续查询。

## 8. 本轮真正需要优先精读的近邻

1. ReFormeR：看成功 query pair 怎样变成可执行模式，以及如何用当前检索上下文选模式。
2. RRM：逐句对照 experience schema、OQR、触发器、适用性、query-only 和生命周期，避免重造已有系统。
3. S2G-RAG / ReflectiveRAG：只选一个作为 FRESH 主基线；重点是证据状态、gap 到 query、停止实现，而不是将其拼进新颖性列表。
4. Useful Memories Become Faulty：读 episodic-only、公平经验暴露与抽象失效的实验；决定我们的 raw-pair 对照。
5. When Continual Learning Moves to Memory：读 §2.3、§3.3、附录，理解伤害分解、跨任务迁移和表示粒度。
6. ERSkill：读验证集 rollout table、capability/deploy 分离与 oracle 保证的范围；不急于复刻其演化系统。
7. LivingRAG：了解最新记忆增强 RAG 的写入支持门、结构化经验及在线协议，作为补充而非基础术语入门。

最值得保留的立意是“来源正确的经验，在新问题上仍可能不适用”。这个现象已有论文，GrowRAG 的机会在于为 **查询修复** 做出有效、便宜、可评估的选择方法。是否比已有方法好，必须由上述实验决定；本轮检索不能保证没有相似工作。
