# 查询侧可信复用层：实施路线

更新日期：2026-08-19
状态：路线已确认，M0 已完成，下一步进入 M1 真实数据接入

## 总目标

先回答一个可证伪的问题：

> 在第一次正式检索前，我们能否只复用“历史上可靠、当前又适用”的查询变换，并在保留有效收益的同时减少把原本正确查询改坏的风险？

第一版不训练大模型，也不承诺数学安全保证。每个阶段都有明确止损点。

## M0：可信层核心合同（已完成）

交付：

- 来源经验卡与目标题查询计划分离；
- candidate / active / quarantine / retired 账本；
- 历史 reliability 与当前 applicability 分离；
- 只输出 DIRECT / REUSE 的检索前 gate；
- full-information oracle 分析器；
- 版本、预算、防泄漏和确定性测试。

完成情况：核心单元测试全部通过；可信门与离线 candidate-set oracle 均有可重复运行的合成示例；经验库、配置、请求和查询计划可从磁盘严格加载，重启后决策一致。

## M1：小型 Oracle 可行性

数据顺序：

1. TREC-RAG query variants；
2. HotpotQA distractor 500–1,000；
3. 少量人工核验错误案例。

回答：

- 历史候选中是否真的存在能改善当前题的变换；
- `DIRECT 正确 → REUSE 错误` 是否达到值得研究的规模；
- 收益是否只是来自更多查询数或更长上下文。

若固定预算下 oracle 都没有收益，则不训练 gate，转成迁移边界/负结果或检索后修复路线。

## M2：无需训练的可信 Gate

比较：

- always DIRECT；
- always REUSE；
- random / nearest history；
- reliability only；
- applicability only；
- reliability + applicability；
- QPP query-variant selection。

目标不是声称“绝不出错”，而是在 dev/calibration 上冻结阈值后，画出真实的 risk–coverage 曲线：复用得越少是否真的越安全，以及损失了多少收益。

## M3：主数据集与严格迁移

主数据：HotpotQA fullwiki + 2WikiMultiHopQA。经验只从 support/train 建立，阈值只在 dev/calibration 冻结，test 不参与晋升或选择。

同时报告：

- 标准官方切分；
- 去除同答案、同实体、同 gold 标题、同关系模板和近重复问题后的 strict-transfer 切分。

只有 strict-transfer 仍有收益，才可以讨论“查询变换经验具有跨题迁移性”。

## M4：无 Gold 与真实使用

先在有 gold 的数据上把 gold 对控制器隐藏，仅允许 QPP、query–experience 匹配、检索稳定性或多个 verifier 的一致性。实验结束后再揭示 gold，检查 proxy 是否真能预测 benefit / harm。

强化学习、contextual bandit 和 EMA 都不是这一步的默认答案：

- 没有可靠奖励，强化学习也不知道什么是正确；
- EMA 只能平滑近期可靠度，不能证明当前问题适用；
- bandit 只在存在可观测在线反馈后再考虑。

## M5：扩展，而非第一版负担

按实验结果选择：

- 加入检索后 FRESH_REPAIR 回退，形成更完整的修复闭环；
- 做可回滚 ERM overlay；
- 比较 query pair、typed pattern 和压缩轨迹笔记；
- 在语料、索引或领域漂移时加入 EMA/变点检测；
- 若规则 gate 与 oracle 仍有明显差距，再训练小控制器。

## 当前最近的三个动作

1. 完成核心合同和测试；
2. 把公开 query variants 转成 Gate 1 CSV；
3. 先看 oracle helpful coverage 与 harm，再决定是否投资真实 gate。
