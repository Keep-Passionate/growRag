# 槽值查询消融：真实结果、科研教学与下一步

## 先看结论

这轮已经执行，不是模拟或实验计划。固定旧历史动作已经填出的槽值后，原历史查询在16题的**累计标注证据覆盖**上，没有胜过两个简化控制；两个控制各有2题更好。真正能删除固定动作词的9题也没有观察到固定词的额外覆盖收益。

因此，目前不能把历史带来的全部证据增量归因于“学到的动作规则”。但**不能据此说记忆完全无用**：这些槽值仍是在历史动作影响下产生的，没有证明无历史方法同样能选对、填对它们。

下一步保持既定A路线，不先训练路由器、不覆盖旧成绩；先通过条件观察接口，再在未见开发题上检查适用条件。同时，为后续完整系统比较保留“同槽值、简化查询”的强控制，避免用复杂经验卡战胜一个过弱对照。

## 1. 我们到底执行了什么

上一轮99个共同完成开发题中，历史分支实际追加检索的全部16题进入本实验。**不是从中只挑成功题**，也不是16道新独立测试题。

固定因素：原问题、同一初检证据C0、历史选择、历史槽值、76,691段共享封闭语料、BM25索引、top6、并集去重、Reader展示窗口。此次没有再次让LLM改写。

每题真实执行原问题和三个修复query，总共64次CPU检索。即使query相同也照实检索，没有缓存后虚计调用。计时合计28.33秒，仅指此次本地检索，不是完整系统线上延迟。

```text
旧封存历史动作、槽值
        ↓ 不看gold构造全部查询并封存
同一原问题 → 初检C0
        ├─ 原历史query        → 文档H  → C0∪H
        ├─ 只拼实际引用的槽值 → 文档S  → C0∪S
        └─ 原问题＋相同槽值   → 文档Q  → C0∪Q
        ↓ 三路独立，不互相累计
全部64次检索封存 → 只投影这16个旧许可ID的gold → 覆盖评分
```

S不一定只含实体：槽值可能包含属性、完整query。不能把整个控制统一叫“仅实体查询”。这也不是可部署的免费无记忆系统，生成槽值的前序成本仍然存在。

## 2. 真实数字：同时报告整体与结构组

这里的覆盖，是每题命中的官方支持句数/该题支持句总数，再对题取平均。比如2/3表示3条标注支持句命中2条。不是答案准确率，不是EM或F1，也不是自动证明证据充分。

本轮原文覆盖与展示窗口覆盖相同，没有观察到窗口截断导致的差距。

| 固定槽值条件下的查询 | 全部16题：C0并集覆盖 | 真正含固定动作词的9题：C0并集覆盖 |
| --- | ---: | ---: |
| BASE：仅原问题初检 | 73.96% | 68.52% |
| 原历史query | 82.29% | 79.63% |
| 只拼槽值 | 87.50% | 83.33% |
| 原问题＋槽值 | 87.50% | 88.89% |

全16题初检已有全部标注的7题；原历史修复后10题完整，两种控制各12题完整。控制完整题数相同，不代表命中的是同一组题。

| 原历史query减去控制 | 全16题：胜/负/平 | 固定词9题：胜/负/平 |
| --- | --- | --- |
| 减去“只拼槽值” | 0 / 2 / 14 | 0 / 1 / 8 |
| 减去“原问题＋槽值” | 0 / 2 / 14 | 0 / 2 / 7 |

全16题这两个差值均为平均−5.21个百分点。这里的“负”是**相对控制少获得证据**，不是把BASE正确答案改错，也不是证明某张卡在所有任务上有害。

其余结构组不能掺进来冒充规则消融：

- 4题本来就是原问题＋槽值；它与Q控制完全同query、同有序文档。
- 3题整个query从槽直通；它与S控制完全同query、同有序文档。
- 2个直通query本来已包含原问题，再拼原问题只重复词，在本地去重词BM25下排序不变。

这些预先登记的负对照都符合预期。相同查询的重复检索不算额外独立成功，也不给经验卡增加可靠度。

## 3. 为什么还要看“修复query单独检出什么”

| 查询 | 16题修复top6单独覆盖 | 16题C0并集覆盖 | 新增段落总数 |
| --- | ---: | ---: | ---: |
| 原历史query | 63.54% | 82.29% | 56 |
| 只拼槽值 | 65.63% | 87.50% | 64 |
| 原问题＋槽值 | 84.38% | 87.50% | 23 |

“原问题＋槽值”新增段落更少，却达到更高覆盖；**检索到更多新文档，不等于检索到更多有用证据**。

原历史query相对“只拼槽值”，单独top6实际有1胜/2负/13平；相对Q是0胜/7负/9平。9个固定词动作在单独top6上仍没有胜过任一控制。

必须保留那个1胜的反例：不能把“累计覆盖没有更好”扩大成“所有query质量都没有更好”。初检证据可能遮住新检索的错误。

## 4. 四个可以直接审阅的案例

### 4.1 固定词干扰：Hunter's Prayer / Rome

- ID：`5abd007d554299700f9d7955`。
- 原问题：哪个《The Hunter's Prayer》演员还在《Rome》中饰演Marcus Agrippa？
- 历史query：`Alan Leech Rome release year`。
- 控制S：`Alan Leech Rome`。
- 原历史C0并集2/3；S和Q均3/3。

真实排序：S在第5位带回《The Hunter's Prayer》，原历史top6没有这一段；Q在第3位带回它。固定词`release year`与原问题寻找演员交集不是同一个目标，本例去掉它改善了检索。

同时发现槽值`Alan Leech`与检出的标题`Allen Leech`不同。我们**不纠正这个拼写再重算**；三个修复query仍用相同旧槽值，所以本轮隔离的是查询形式，而非槽值纠错。

教学：模板表面上的属性错位和槽值绑定质量是两个变量。未来需要分开测，不能一起修好后把增益全归给适用条件。

### 4.2 机械拼接不一定改变BM25：My Name Is Lenny

- ID：`5a7cccab554299683c1c6383`。
- 历史动作：原问题＋`My Name Is Lenny`。
- 片名本来就在原问题中；本地BM25使用去重词集合，重复拼接没有添加检索词。
- 原历史返回与C0完全相同的6段，新增0；累计覆盖1/2。
- 只搜`My Name Is Lenny`在第1位返回电影段，新增6段；累计覆盖2/2。

修复query单独覆盖两者都是1/2，但检出的是不同支持内容：S补的是C0缺少的另一半。

教学：改写文本“看起来变长”并不等于检索器看到有效变化；单独命中率相同也不等于互补价值相同。控制器要考虑当前证据，而不只是query长度或相似度。

### 4.3 原问题的关系锚点有价值：Mandalay Bay

- ID：`5a8d10c65542994ba4e3dbda`。
- 原问题询问Las Vegas Stadium在某个43层度假酒店的西侧。
- 历史query：`Mandalay Bay headquarters city`。
- 只拼槽值：`Mandalay Bay`。
- 两者C0并集都是1/2；原问题＋槽值是2/2。

Q真实在第3位检出`Las Vegas Stadium`段，H和S都没有。原问题中的体育场及位置关系保留下来，才检到了另一侧证据。

教学：识别到正确实体还不够。需要保存“答案要证明什么”和“这次query用什么定位文档”的区别。不过不能因此规定所有query都必须完整保留原问题——上一个电影例恰好反对这个万能规则。

### 4.4 删得太短也会歧义漂移：The Beginning

- ID：`5a77d03a55429967ab1052b4`。
- 原问题：哪个出演《The Beginning》的人也是职业滑板运动员？
- 历史query保留原问题并再次拼片名，单独覆盖1/2，仍是初检那6段。
- 只搜`The Beginning`后，top6变成摔角赛事`The New Beginning...`，单独覆盖0。
- 累计C0并集仍都是1/2，因为旧初检已有的支持没有删除。

教学：累计覆盖不下降，不等于新增查询没有偏题。未来要同时记录互补证据、无效文档、对象歧义和最终答案，而不能用“append-only不会丢证据”冒充系统安全证明。

## 5. 旧三个历史证据正例还成立，但归因缩小了

旧首修诊断中，历史相对FRESH多补证据的三个例子都保持：

- Gordie Howe：删掉`nicknames aliases`后，与原历史**同序返回完全相同的6段**。昵称词未显示独立贡献。
- Spotlight导演：删掉`release year`仍检出电影段，且电影段从原历史第3位变成S/Q第2位；三路累计均3/3。不能把导演证据归功于发行年份词。
- Saw V / Costas Mandylor：S、Q、原历史累计都3/3。

三个例子原受控答案仍是FRESH/历史都EM1。本轮没有新答案，不能新增“历史修好了三道错题”的说法。

这支持一个**待验证的较窄假设**：有用的历史信息可能主要帮助选择定位实体和填参，而不是机械复制查询尾巴。下一个未见题实验仍可能推翻这个假设。

## 6. 为什么还不训练路由器

路由器是在已有候选中选择，不会凭空发明更有用的动作。

旧99题受控QA尚无“仅历史答对”的题；本轮也没有让历史规则文字产生新的独立累计覆盖优势。直接训练选择器，可能只学会绕开历史，从而得到一个“永远FRESH”的退化系统，而没有回答历史什么时候真正值得持有。

当前先分清四个环节：

1. **经验检索**：有没有把适当卡片放进候选？
2. **适用判断**：当前问题/证据是否支持使用这个动作？
3. **槽值绑定**：实体、作品、角色有没有填对？
4. **查询呈现**：采用实体短查询、原问＋实体、属性规则，哪个适合当前缺口和检索器？

研究对象还是可信历史查询修复，不是突然转成通用query优化。候选/槽值/呈现的控制实验，是为了排除“经验看起来有效，其实只是填到了一个实体”的竞争解释。

## 7. 下一步：按门推进，而不是一次加所有模块

### 第一步：两阶段条件观察接口，保持原门槛

- 用原32行开发合同定位当前证据、判断固定动作；最多64请求、无重试，不降低原准入标准。
- 固定44张现有可调用卡，不修改SELECT/FILL，不生成新动作，不回写永久记忆。
- 目的：确认“支持/冲突/未知”输出可追溯、接口可靠。单测通过不等于真实模型通过。
- 当前两阶段代码已实现；**实际API诊断仍未执行**，需要预算策略确认。

### 第二步：通过接口门后，再做40个新自然开发题

- 仍是此前约定的影子条件验证、两次总检索上限，不使用旧100题训练条件或路由。
- 先封存全部预测/动作，再开许可标签；维持旧条件对照，不根据途中成绩改prompt。
- 重点解释被拒/被放行卡，区分实际执行伤害与“没动作所以没修好”。
- 目的：测量条件是否真能区分，而不是先让它变成严格过滤器。

### 第三步：单独新版本做查询呈现控制，不能夹在第二步里偷换

- 预先冻结纳入规则、同一候选/槽值来源和相同检索预算。
- 两条主要比较：历史动作 vs 同槽值简化查询；历史辅助绑定 vs 不读历史、独立现场绑定。
- 两条回答不同问题，不能合为一句“有记忆优于无记忆”。后者才会检验卡片对实体/角色发现有没有真正帮助。
- 再加入同预算的验证式FRESH，排除只是历史比FRESH更愿意多搜一次。
- 所有新答案比较要真实Reader调用并记录输入、引用、token和费用；不得用本轮覆盖结果补造EM。
- 这一步是待细化的独立协议，**本轮没有增加付费臂或改第二步门槛**。

### 第四步：出现独立机会后，才学习路由与条件

- 用独立来源/训练角色产生配对标签，不用旧测试题更新长期记忆。
- 先固定候选池，逐项删适用条件，检验误用与误拒，再训练轻量选择器。
- 同时报告历史实际调用率、修复原错、损害原对、证据增量、API和检索成本。
- 只有准确率变化而不能归因于历史/条件，仍不足以支持核心贡献。

## 10. 这一步教我们怎样做科研

不要只问“加上记忆有没有涨分”。更有价值的问题是：**删掉声称带来收益的那一部分，收益还在不在？**

本轮固定槽值，删除模板固定词，就是一次归因实验。保留全部16题、结构性负控以及The Beginning反例，是为了避免把自己希望看到的故事当结果。

本轮未观察到固定动作词的额外累计标注覆盖收益，这是正常科研发现，不需要立刻扩大库追分。现在更明确的任务是验证：历史有没有帮助得到合适的定位实体、目标关系和执行条件，以及它们是否比同预算现场修复更有价值。
