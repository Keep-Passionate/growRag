## 结论

先用当前电脑做程序、CPU 检索和实验记录，以用户选定的真实 API 运行改写与回答。当前阶段不需要先申请大型 GPU。若实验室已有机器可借，优先 24 GB 显存、64 GB 内存的 Linux 工作站；若计划同时比较 14B 原精度和 32B 量化，48 GB 更从容。这里是容量建议，不是运行速度承诺。

模型服务、地区、固定版本、发送的数据和费用上限确定前，仅运行离线测试；不能把离线测试输出或本对话里的示例改写标成 API 实测。

## 2. API 与本地模型的取舍

| 方案 | 可从什么时候开始 | 优势 | 代价或限制 |
|---|---|---|---|
| 当前电脑＋真实模型 API | 接通程序、确认服务配置与预算后 | 不等显卡；便于先找出方法是否有效 | 按调用付费；需记录服务版本，外部服务可变 |
| 实验室 24 GB 显卡 | 后续需要固定开放权重对照时 | 8B 原精度、14B 4-bit 是较稳妥起点 | 32B 4-bit 可能勉强装下，但长上下文和并发余量少 |
| 实验室 48 GB 显卡 | 做更强本地模型对照时 | 14B 原精度、32B 量化更宽裕 | 仍需配置推理软件、保存权重与运行日志 |
| 实验室 80 GB 显卡 | 明确要做 32B 原精度或更高吞吐时 | 显存余量更多 | 当前单步原型不必先占用；80 GB 也不是任意上下文与并发都能运行 |

CPU 检索与模型推理是两个资源问题。使用 API 不代表检索免费或不要内存；检索语料规模、BM25 索引实现、是否使用密集向量，决定 CPU/RAM/磁盘需求。首轮先用公开 HotpotQA 的限定候选语境或明确标记的小语料检索做工程核验，不能把这种成绩称为全维基开放检索成绩。

若借实验室机器，建议登记：Linux 版本、GPU 型号/显存、驱动、可用 RAM、SSD 空间和可用时段。64 GB RAM 与约 200 GB 可用工作空间是后续小到中等规模实验的预留建议，不是全量语料的精确测量需求；全量索引另行盘点。

## 3. 本地 Qwen 的显存：不能只按模型权重大小计算

Qwen 官方给出的一个实测设置是 H20 96 GB、Transformers、批量 1、输出 2048 token。以下摘取输入 6144 token 的内存列，保留官方 MB 单位；这不是我们在 RTX 4060 上测得的结果。

| 模型 | BF16 内存（MB） | AWQ-INT4 内存（MB） |
|---|---:|---:|
| Qwen3-8B | 16811 | 7113 |
| Qwen3-14B | 29495 | 11020 |
| Qwen3-32B | 64583 | 20795 |

原精度 BF16 约用 16-bit 保存权重；INT4 用更低精度压缩，能省显存但需要核验精度变化和算子兼容性。上下文缓存、临时计算空间、并发请求和推理框架预分配都会额外占显存。输入变长还会继续增加占用，所以“32B 4-bit 权重约 16 GB，因此 16 GB 卡就够”是不可靠的推断。[Qwen 官方速度与显存基准](https://github.com/QwenLM/Qwen3/blob/main/docs/source/getting_started/speed_benchmark.md)

据此做容量估算：单并发、中短上下文时，8B INT4 可按约 7–10 GB 预留、14B INT4 约 11–16 GB、32B INT4 约 21–30 GB；这些是含余量的规划区间，不是硬性最低配置。更长上下文、多并发或不同框架可能超出区间。训练还需要梯度、优化器等额外资源，不能套用推理表。首阶段不训练；以后的小选择器也应单独估算，不默认要微调整个 LLM。

## 4. API 推荐：先接通一种通用接口，不锁死厂商

建议优先候选为阿里云百炼的文本 Qwen-Plus 固定快照，首轮保持改写模型、回答模型、模式和参数不变。官方价格页当前列出 `qwen-plus-2025-12-01` 等带日期版本；这是候选例子，不等于已验证用户账户所在地区可以调用。运行前在用户控制台确认可用版本、功能、地区和价格，不盲选 `latest`，也不为“最新”频繁换模型。[官方模型价格与版本表](https://www.alibabacloud.com/help/en/model-studio/model-pricing)

百炼有 OpenAI-compatible Chat 接口。接入配置应分开保存提供方、地区、base URL、模型 ID；密钥只从本地环境读入，不能进入 Git 或日志。API Key 与地区匹配。2026-09-04 英文兼容文档的 Beijing 示例表与其迁移说明有地区不一致之处，因此以用户控制台和所选地区的正式接入配置为准，不自动复制表格 URL。[官方兼容接口说明](https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope)

结构化改写可先采用所选模型支持的 JSON Object 模式，提示词明确要求 JSON，并进行本地字段/类型校验。JSON Object 只约束 JSON 格式，不保证结构完整或内容正确；JSON Schema 的支持范围要按所选模型核验。旧 Qwen 系列应特别检查非 thinking 模式要求。对证据真实性、缺口是否合理，仍要另做业务校验；返回合法 JSON 不能当作“没有幻觉”。[官方结构化输出说明](https://help.aliyun.com/en/model-studio/qwen-structured-output)

这里的 OpenAI-compatible 指请求/响应格式相似，不意味着我们已经调用 OpenAI 模型，也不意味着可以借用当前对话模型作为实验后端。

## 5. 怎样证明真的是一次 API 调用

以下是 GrowRAG 的审计设计要求，不是已经全部实现或已经取得的实测记录：

1. 每条结果标明来源：`mock`、`live_api`、或 `replay_of_live_api`。从缓存回放时必须链接原始真实调用记录，不能算成又调用了一次。
2. 记录请求时间、所选 provider/region/model、完整实验提示词或其可追溯制品及哈希、生成参数、数据与分支 ID。
3. 记录实际返回文本、响应 ID、服务返回的 model、finish reason、usage、耗时和错误；不捏造缺失字段，不记录 Authorization 头。
4. 只有实际联网得到的响应才标为 `live_api`。模拟的 HTTP 单测仍是 `mock`，即使其中写有假的 request ID 或 token 数。
5. 截断、非法 JSON、超时和服务错误保持为失败/不完整；不偷偷换模型、重试到成功后删掉失败记录，或用人工编写答案补齐。
6. 独立评价器读取 gold；发送给改写器和回答器的 payload 不含目标题参考答案、supporting-facts 标签或由这些标签构造的“真实缺口”。

阿里兼容接口响应包含响应 ID、model、finish reason、token usage 等计量字段；字段有助于追溯实际传输，但并不是数学上的真实性证明，必要时可与控制台用量核对。[官方响应字段](https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope)

## 6. 假模型不是费用估计器

假模型是离线测试替身：例如对一份固定测试输入返回预先写好的 JSON，让程序检查 FRESH/REUSE 是否隔离、字段是否正确、gold 是否越界、异常是否被保留。它没有理解能力，不会检验改写质量，也没有真实 API 账单。

假模型结果只能证明“程序在这组测试条件下按预期运转”，不能证明“Qwen 已真实改写”“经验有效”或“真实费用是多少”。本轮没有调用付费 API，也没有读取或打印 API Key。

## 7. 费用估计与真实费用分开

先保存可变价格配置：币种、地区、model ID、计费日期、输入/输出/缓存/思考 token 的单价与适用长度档位。不能拿国际美元价当中国控制台人民币价，或忽略 thinking 输出计费差异。

估计总费用 = 各次调用的输入 token × 对应输入单价 + 输出 token × 对应输出单价，再按服务规则计入其他计费项。若采用“每百万 token”的价格，先除以一百万。执行后用服务返回 usage 更新记录，最终账单以提供方结算为准。

首批真实 pilot 只用于工程调试和估算 token/耗时，不使用最终冻结测试题。建议从约 10 道开发题起，并设置用户确认的费用上限、调用数上限和输出长度上限；这只是待确认的规模建议。本轮不预先承诺一个人民币金额，也不启动调用。观察实际长度与错误率之后，才能可靠推算 100/500/1000 题以及多分支的预算。

配对实验中的公共首次检索只执行一次，但共享成本既要单独记录，也要在独立部署成本对比时采用同一摊分规则。多跑的 FRESH 候选、记忆检索、选择、重试和额外 judge 不能从某一方法的费用中省略。[官方价格与计费差异](https://www.alibabacloud.com/help/en/model-studio/model-pricing)
