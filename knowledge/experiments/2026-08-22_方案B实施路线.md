# 方案 B「可信自适应查询修复」实施路线

更新日期：2026-08-22
状态：主方向已确认；M0 数据合同已完成，下一步进入 M1

## 总目标

先回答一个可证伪问题：

> 相比始终使用 BASE 或每题现场 FRESH repair，跨题复用经过验证的 query-repair episode，能否在固定预算下提高答案/证据质量、减少现场 LLM 调用，同时把 `BASE good -> REUSE bad` 控制在可接受范围？

## M0：稳定数据合同

状态：已完成第一版实现与自动测试。

交付：

- `RunContext` 注册表；
- append-only `QueryEpisode`；
- append-only `VerificationEvent`；
- 可选 `DocumentSession`；
- 版本化 `ExperienceCard`；
- schema 校验、冻结规则、来源指针与防泄漏测试。

已落实的约束：BASE-first 状态机；每 turn 单查询归因；final evidence 来源闭包；所有 episode 完成即冻结；验证只追加；配对必须同题、同 context、同预算；失败不进入 serving memory；ACTIVE 卡必须经过可重算的来源/收益/伤害注册校验。

## M1：冻结 BASE 与 FRESH，不使用历史经验

先接一个固定文本 RAG，首选公开、简单、可复现的 BM25 或 dense BASE。冻结：

- corpus snapshot；
- chunk/index policy；
- retriever/top-k/context budget；
- generator；
- state judge / fresh repair prompt。

动作：

```text
BASE
FRESH_REWRITE
FRESH_DECOMPOSE
FRESH_GAP_QUERY
HYDE（dense arm）
QUERY2DOC
```

数据：

1. 先用 HotpotQA/2Wiki 各 200–500 题跑通；
2. TREC-RAG/QPP 资源校验 retrieval vs answer utility；
3. MuSiQue 小样本检查 insufficient/no-progress 状态。

Gate：若 FRESH 修复相对 BASE 在公平预算下几乎没有 oracle 增益，不建长期经验库；先修正 BASE、prompt 或研究对象。

## M2：Episode → candidate card

只从 `beneficial_success` 生成 candidate：

- 修复相对 BASE 有正增益；
- gold answer/supporting facts 或人工强验证；
- 保存具体 q→q' 在 episode；
- 抽象卡只保存 gap/operator/conditions/evidence contract；
- 卡片保留来源 episode/turn 指针。

比较：

- raw episode only；
- abstract card only；
- dual representation；
- 一次成功即 active（危险对照）；
- 独立题验证后 active（本方法）。

Gate：strict cross-entity/cross-document 切分上的 oracle helpful coverage 必须大于近邻/随机历史，且不是同答案或模板泄漏。

## M3：BASE / REUSE / FRESH 三臂 oracle

在 train/dev 对每个目标题执行固定候选集：

```text
BASE
REUSE(candidate 1..K)
FRESH(operator 1..J)
```

相同预算记录：

- answer score；
- supporting-fact recall/precision；
- retrieval Recall/MRR/nDCG；
- benefit / neutral / harm；
- conditional harm `P(REUSE bad | BASE good)`；
- retrieval calls、tokens、latency。

Oracle 只用于上界和生成开发标签，不是可部署 router。

Gate：如果 REUSE oracle 不比 FRESH 或 BASE 提供可用的 accuracy–cost Pareto 改善，则不训练 controller；把结果写成经验迁移边界或回到更窄问题。

## M4：冻结 prompt 的规则控制器

完整控制流：

```text
BASE -> state/gap
  -> ANSWER
  -> trusted & applicable REUSE
  -> FRESH
  -> STOP_ABSTAIN
```

比较：

- always BASE；
- always FRESH；
- nearest history / always REUSE；
- Adaptive-RAG complexity router；
- QPP variant selector；
- S2G/Skill-RAG 风格 fresh repair；
- RRM-like experience reuse；
- reliability only；
- applicability only；
- reliability + applicability；
- 完整方案加 harm gate。

阈值只在 calibration/dev 选择并冻结。测试集不建库、不晋升、不调 prompt。

## M5：训练小 controller

仅当规则控制器与 oracle 有明确差距时训练。

输入：

- query 特征；
- BASE 检索后的 sufficiency/gap/progress；
- top experience 的 reliability/applicability/harm/cost；
- 剩余预算。

输出：`ANSWER / REUSE_REPAIR / FRESH_REPAIR / STOP_ABSTAIN`。

顺序：

1. 逻辑回归；
2. 小型树模型；
3. 小文本 encoder classifier；
4. 只有监督标签和反馈闭环仍不足时才讨论 bandit/RL。

## M6：外部泛化

- 第二个 retriever family；
- 第二个 corpus/domain；
- 第二种 BASE（例如 GraphRAG/Hybrid）；
- RAGRouter-Bench 作为跨范式压力测试；
- environment strict vs capability-aware matching；
- EMA/Kalman-inspired priority 作为非核心扩展。

## 主数据集分工

| 阶段 | 数据 | 主要 gold | 用途 |
|---|---|---|---|
| M1 小型调试 | TREC-RAG/QPP variants | qrels、nuggets/answer judgments | 校验 variant、retrieval utility 与 answer utility 不同 |
| M1–M4 主实验 | HotpotQA fullwiki | answer + supporting facts | query repair、多跳 gap、跨文档迁移 |
| M1–M4 主实验 | 2WikiMultiHopQA | answer + evidence/supporting info | 关系型多跳与 strict transfer |
| M3–M5 压力 | MuSiQue | answer + supporting paragraphs | 困难组合、证据不足、无进展与弃答 |
| M1/M6 IR | BEIR / BRIGHT / TREC DL | qrels | query operator 和跨 retriever 外部有效性 |
| M6 | RAGRouter-Bench | 多范式运行结果/质量成本指标 | Vanilla/Graph/Hybrid/Iterative BASE 外部验证 |

## 首篇论文的最小范围

首篇不同时解决：

- 多种 BASE 之间的在线路由；
- 无 gold 的在线自我训练；
- 失败经验 serving；
- RL/bandit；
- EMA/变点检测；
- 新的 stopping 理论；
- 新 query rewriter。

这些可以作为后续扩展，避免方案 B 被扩成不可归因的大系统。
