## 1. 本轮应当收紧的中心问题

用户希望把“学到一条经验”与“值得永久影响以后行为”分开；不反复改写旧摘要，优先两三层以内的浅层表示；保留轨迹供核查，但不把历史答案交给当前回答器。用户还强调：降低有害复用必须同时保留有用修复，不能用永远不用经验来取巧。

建议把三个决策分开研究：

1. **留不留下：** 这条经验是否值得占据跨题执行库的位置？
2. **现在用不用：** 当前问题和状态是否适合它？
3. **改版替不替换：** 新卡是否值得替换旧卡，还是保留旧卡/并列保留更好？

它们不是同一个成功率。某张卡很少用，但能救回重要的特定问题，可以值得持有；另一张卡经常被检出，却从不比 FRESH 更好，就不应仅凭热度上升到执行库前列。

更具体的候选方法主线是：**冻结已经形成的操作内容，追加独立的收益/反例记录；需要改变操作或适用范围时，生成可追溯的新候选，并与旧方案正面对比，优先从原始经历重新提炼。** 这比“持续修正适用范围”更可执行，但仍需与已有条件记忆、保留/整合机制比较，不能先宣布新颖。

## 2. ERM 的 transient / persistent：借鉴的是行为持续性

本项目把用户所写的 EMR 按此前语境理解为 **ERM / RAG without Forgetting**，不是新建一篇 EMR 文献。

ERM 确实对比 transient 查询扩写与 persistent 检索改进：前者通常只影响本题，后者把经验证的扩写信号写入文档 key，改变未来检索。它还进行原子贡献分配及有界更新。因此这不是它原文命名的“双层卡片存储”，也不支持“ERM 不修改旧记忆”。我们借鉴选择性持久化，但继续冻结底层索引，把持久化位置放在外部程序性经验库。[ERM §1、§4](https://arxiv.org/html/2602.05152v1)

### 2.1 物理保存与执行资格是两件事

| 对象 | 本题结束后怎样处理 | 是否影响后续 query |
|---|---|---|
| transient 工作上下文 | 从活动上下文退出；按审计策略保留实际记录 | 不自动影响 |
| 审计档案 | 保存 query、证据出处、尝试、反馈和来源 | 不作为默认在线候选；模型不能任意读取整个档案 |
| persistent 候选卡 | 可以保存到磁盘，等待独立验证 | 默认不进入正式服务；只在显式诊断实验中测试 |
| persistent 执行卡 | 在已验证的条件和版本范围内可被选择 | 可能影响，但仍可被当前路由拒绝 |

“本题结束消失”应理解为退出后续执行权限，而不必删除审计记录。`persistent ≠ trusted ≠ 每次都用`。保存文件不代表允许它进入下一题 prompt。

审计用途与执行用途也不是新增两个推理层。仍以 QueryEpisode / PRE SourcePair 为来源，以 ExperienceCard 为跨题操作表示；DocumentSession 继续后置。

### 2.2 为什么不把所有正确源题都做成执行卡

源题答对可能来自原检索、模型已有知识或随机生成；操作可能只适合一个对象，也可能与现有卡完全重复。建议分两步：先保存最小真实记录；只有出现可描述且值得验证的查询变化时，才提炼候选。避免每题强制生成一段“人生经验”。

## 3. 怎样判断“值得持有”，不只是“曾经成功”

### 3.1 最少考察五件事

| 维度 | 应问的问题 | 反例 |
|---|---|---|
| 可追溯 | 操作与条件是否指向真实来源，能否核查 | 卡写了“应加时间”，原记录其实没做过 |
| 迁移增量 | 独立问题上，REUSE 是否优于同状态 FRESH | 两者都答对，不能记成额外答案收益 |
| 有害影响 | 是否把 BASE 或 FRESH 能做好的题改坏 | 新约束删掉否定或改变比较对象 |
| 不可替代性 | 现有库是否已能提供同等操作 | 两张相同卡互相挤占 top-k |
| 持有成本与需求 | 它是否值得占据候选空间、上下文和验证预算 | 大量热门但无增益摘要压住少量有用经验 |

这五件事先分开记录，不急于加权成一个神秘的“置信度”。检索次数、使用次数、源题成功率，都不能单独代表长期价值。

### 3.2 两个不同的配对问题

**问题 A：经验有没有额外作用？**

```text
REUSE(当前题，候选经验) − FRESH(相同题和状态，不看历史)
```

**问题 B：这张卡是否值得占据库中的位置？**

```text
固定策略使用 M 的效果 − 同一策略使用 M 去掉该卡后的效果
```

M 是冻结的经验库。第二个对照允许选择器在删卡后使用别的卡或 FRESH，因此衡量该卡对当前库的边际价值。删除会改变候选排序，这也是持有价值的一部分；若只想分析正文作用，另固定选中卡做内容移除。两者不能混成一个“因果分数”。

这仍是离线诊断，不建议每题给每张卡都跑一次删卡实验。先对拟合并、重复或频繁占据候选位的少数卡做检查；费用、样本选择和适用分布要公开。稀有卡数据不足时记为不确定，可留在有容量限制的候选池，不自动上线也不自动判垃圾。

还要防止批量淘汰的陷阱：两张重复卡各自移除都没有损失，不代表两张可以一起删除。应保留代表卡，或每次修改候选集合后重新检查；有互补关系的经验也不能只用单卡价值机械排序。

### 3.3 建议的晋升路径

```text
本题临时操作
  → 不可变来源记录
  → 值得验证时生成候选
  → 独立训练问题上的 REUSE/FRESH 反馈
  → 检查收益、伤害、覆盖与冗余
  → 仅在验证支持的范围内进入执行库
```

“多次”不能直接写成两次成功就 trusted。需要区分独立题、同题重复、来源重叠和条件覆盖；具体门槛在校准池选择。当前代码中的演示门槛不是统计安全保证，更不是从论文直接得到的最优值。

## 4. 浅层记忆：限制的是派生深度，不是文件版本数

Useful Memories v2 区分首次压缩损失、旧抽象影响后续抽象，以及原地改写。其保留、删除与整合对照支持显式控制整合；论文也已有来源链和快照。**新建文件而不覆盖，仍可能是摘要改摘要。** 它没有给出普遍有效的“最多两三层”阈值。[§6.4 与附录 L.2](https://arxiv.org/html/2605.12978v2#S6.SS4)

建议采用以下可审查定义，作为我们的待验证工程约束：

```text
深度 0：无历史经验输入的基础来源记录（首版使用 FRESH 来源）
深度 1：直接从原始记录提炼一张操作卡
深度 2：以已有卡正文为输入，生成新卡或合并卡
深度 3：继续摘要深度 2 的卡 —— 默认不执行
```

这相当于“原始记录＋一代卡＋至多一代派生卡”三层以内。**默认优先深度 1；建议上限 2；深度 3 只作为隔离消融条件，不是已获授权的上线设置。** 用户认可的是浅层、防漂移方向，具体数值尚待确认和验证。

### 4.1 三种数字不要混淆

- `version`：文件/内容第几版，可以很大。
- 内容派生深度：连续多少代把生成出来的记忆再当作语义材料。
- 反馈记录数：更新过多少次效果统计，不等于改写过多少次经验。

内容输入中包含旧卡时，新深度应为最大父深度加一；要依据实际输入记录计算，不能由模型自报。单纯追加一次成功/失败事件不增加深度。

但修改适用规则虽然未改动作正文，也会改变未来行为：需要新的执行配置/范围版本与重新评估，不能借“只是元数据”跳过检查。永久文档层数则是另一概念，不应把两者都叫三层记忆。

### 4.2 达到深度上限怎么办

按优先级选择：

1. 旧卡仍有效：保留原卡，不为更新而更新。
2. 只是重复：将重复副本从执行视图移出，保留出处与理由。
3. 确实需要概括：取回原始来源和原始反馈，重新提炼候选。
4. 来源不足、无法核查：暂停执行；不再继续润色它。

“返璞归真”的严格含义是：新候选的内容生成只看原始材料和固定提炼规则，**不看旧摘要正文**。新卡生成完以后，可以再与旧卡做去重和版本比较；这一步不能悄悄把旧摘要写回新正文。管理上的“替代旧卡”关系与语义上的“根据旧卡生成”关系要分开记录。

这里还有一道容易漏掉的边界：不能把整个“原始运行 JSON”直接送入提炼器，其中可能内嵌 `decision.memory` 的旧卡正文。只取许可的实际查询、已观察状态、证据引用和反馈摘要；源答案/gold 不复制成程序性建议。原始审计记录也可能来自 REUSE，查询动作本来就受旧卡影响。首轮深度实验统一使用独立 FRESH 来源；以后若从 REUSE 轨迹提炼，必须保留其父卡影响关系，不能通过“先落盘成记录”把旧依赖洗成全新的深度 0。

多份原始记录直接汇总成较抽象的规则，其内容派生深度仍可能只有 1；但抽象范围更广，仍要重新验证。低深度不保证低风险，重新提炼也可能丢信息。

## 5. 允许合并，但不因相似就合并

优先采用“共同索引、分别保留原卡”来处理近重复：把同类卡归组，保留各自前提。只有真有节省和覆盖收益时才做语义合并。

合并候选至少检查：

1. 动作和目标是否一致，而不只是问题词相似。
2. 前提是否兼容，是否能保留必要分支。
3. 原问题的时间、否定、关系方向等约束是否被删掉。
4. 合并后的作用范围是否超出已有支持。
5. 与“旧卡分别保留＋相同选择器”比较，是否值得替换。

若一张卡要求“实体已经唯一定位”，另一张要求“先消歧再检索”，不能合并成“找到实体后查属性”就声称涵盖全部场景。即使两个场景各有成功，也不能推出它们的任意组合都成功。

建议合并后生成新候选，不自动继承父卡最高置信度，也不立即删除父卡。旧事件可以作为来源与分析材料，但不能冒充新正文已经真实执行成功。正式比较保持相同原始来源集合、检索候选规则和 token 上限。

## 6. 当前最小记录结构：已有部分与缺口

当前项目不是一套已统一的持久化平台：旧 QueryEpisode 是 BASE-first 后置轨迹；新 PRE 试验另用独立的 PreSourceRecord 存 BASE/FRESH。旧 ExperienceLedger 的快照又属于更早的 QueryTransformation 模型，不能把三条路径说成已经无缝贯通。

### 6.1 目前真正已有的主要字段

```text
ExperienceCard
  card_id / version / lifecycle_state
  activation：阶段、query/gap模式、前提、反条件、能力要求
  repair：动作类型、动作正文、目标与预期证据
  provenance：来源步骤或PRE来源对
  validation：验证事件引用、收益/中性/伤害计数等
  serving：费用估计、使用次数与时间
  parent_versioned_ids：父版本引用
```

代码：[ExperienceCard](../../src/growrag/experience/cards.py)、[QueryEpisode](../../src/growrag/episodes/models.py)、[PRE 来源](../../src/growrag/experience/pre_sources.py)。

`revised_candidate()` 已会保留旧来源、记录父版本，并清空新候选的验证统计；它不是自动压缩器，也没有限制派生深度。当前 PRE 卡仅为候选，独立迁移试验计数为零，不能宣称已自动可信晋升。

### 6.2 对照用户提出的六组内容

| 用户想要的组 | 当前情况 | 最小补齐方向 |
|---|---|---|
| 观察状态：证据、缺口、异常、失败尝试 | 旧 episode 有 query、证据引用、gap 与动作序列；PRE 来源是另一路径 | 统一引用可见状态快照；失败尝试引用已有步骤，不再复制整段文本；PRE 的未观察状态记 UNKNOWN |
| 候选动作：改什么、不改什么 | ParaphraseBody 已有 rewrite_rule/preserve；ExpansionBody 有 term_roles/grounding_rule | 继续统一外壳、不同正文，不新增一套自由格式大卡 |
| 适用依据：当前观察支持什么 | 卡中已有前提/反条件；有限模式匹配只核查窄范围 | 在本次决策记录中保存“哪个条件由哪个当前证据支持/未知/不满足”，不是把每道新题写回卡 |
| 支持、无增益、退化记录 | 有旧事件/统计，PRE 报告有三个对照；尚未统一回流 | 事件明确比较 BASE 还是 FRESH，保留完整分支引用和结果来源；UNKNOWN 不混成无增益 |
| 来源、版本、当前有效版本 | 有来源和父版本；没有完整内容派生账本 | 增加实际内容输入引用、生成方式、计算出的派生深度；明确哪个版本具备执行资格 |
| 候选、可用、受限、暂停、撤销 | 当前枚举为 candidate/active/quarantine/retired | 不必立刻增加五六个并列状态；范围限制作为与生命周期正交的规则 |

现在的主要缺口不是“再加很多字段”，而是**让每一条反馈明确回答：哪张卡、在哪个独立题、相对什么对照、产生了什么效果。**

### 6.3 建议的小记录：三种对象，不是三套记忆系统

以下是建议接口示意，不是当前已经可运行的 schema：

```yaml
source_record:
  id: source_17
  protocol: post_retrieval       # PRE则引用独立来源对，不伪造gap
  observed_state_ref: state_17   # 当时真实可见的证据/缺口/失败尝试
  executed_action_ref: step_2
  outcome_refs: [result_17]

experience_card:
  id: card_17
  version: v1
  lifecycle: candidate
  stage: post_retrieval
  conditions: [当前证据已唯一确认目标实体]
  action:
    change: 从作品名称转为当前已确认创作者的属性查询
    preserve: [原题身份限制, 原题时间限制]
  source_refs: [source_17]
  derivation:
    mode: extract_from_sources
    semantic_input_refs: [source_17]  # 真正进入生成步骤的内容来源
    depth: 1                         # 由来源依赖计算，而非模型填写
  validation_event_refs: []

feedback_event:
  id: trial_42
  card_ref: card_17@v1
  target_question_id: target_42
  decision_state_ref: state_42
  applicability_check_ref: fit_42
  comparator: FRESH                  # 不再用DIRECT含混代替
  branch_result_refs: [fresh_42, reuse_42]
  feedback_source: gold              # human / judge / proxy另标
  observed_at: feedback_time_42
  eligible_for_update: true          # 正式测试/封闭探针必须false
```

具体分数、异常与成本从分支结果读取，不把整段失败轨迹复制进卡。选择器读取经许可的统计与前提；改写器只读取本题适用的程序性正文与当前绑定；回答器不读取历史卡，把本题检索文档作为事实依据。

目前还未完全做到这么精简：`APISingleQueryGenerator` 会序列化整个 CardMemoryView，来源 ID/hash 等元数据也进入 prompt；虽然没有目标 gold 和源答案分数，但未来应缩小成显式的生成正文白名单。[当前生成适配器](../../src/growrag/query_actions.py)

### 6.4 生命周期与适用范围分开

```text
CANDIDATE：待验证，可在隔离实验中测试
ACTIVE：在已有验证支持的范围内允许被选择
QUARANTINE：暂不执行，等待定位问题
RETIRED：不再参与默认服务；历史保留供审计
```

“范围受限”不是自动落在 ACTIVE 与 QUARANTINE 之间的新级别：每张 ACTIVE 卡本来就应有范围。缩小范围后要记录新的执行条件，检查是否只是记住几个坏题的 ID；扩大范围尤其需要新证据。

审计档案原则上追加、可复查，但不承诺现实系统永远保存所有原文。未来要按隐私、许可、容量与保留期限制定归档策略；删除执行候选与物理删除数据是不同操作，本轮不做删除。

## 7. 反例怎样更新范围，而不把记忆越改越碎

建议先冻结动作正文，把反馈追加到侧边账本。一次失败只产生事件，不让 LLM 立刻重写整张卡。

先定位失败可能在哪层：

- 当前前提未满足，发生错误绑定。
- 前提满足，但此改写不适合当前检索排序。
- 检索证据改善，答案生成却失败。
- 输出没有真正变化，仅出现模型波动。
- 反馈本身不确定或标注不完整。

这些原因不能全部变成“这条经验不可信”。若观察到重复且可解释的适用反例，再提出范围变更；变更必须表达可观察条件，不是加入“除了题号 42、51”。在独立训练/校准题验证后才启用。

旧反馈永远保留其真实对象和版本。仅仅根据老反例写出的新版规则，不能再在同一批反例上通过一次就宣称有泛化能力。

EMA 可以保留为近期效果趋势的工具，但不让它自动修改操作正文。长期配对记录、近期趋势和不确定性分开；使用频率不当作成功次数，无反馈不当作负反馈。

## 8. When Continual Learning Moves to Memory 给我们的具体启发

该文将内容表示与检索组织分开：比较具体轨迹和 Insight，也比较整组经验、单条经验及执行中再次检索。其 ALFWorld/BabyAI 结果提示跨任务表示可能影响正负迁移，但并非所有任务方向都由抽象获胜。它还在学习后续任务后回测旧任务。当前核到 v1，arXiv 标为 Working in progress，未确认正式发表。[原文 §2–4、附录](https://arxiv.org/html/2604.27003v1)、[版本记录](https://arxiv.org/abs/2604.27003)

因此我们不能写“抽象洞见通常必然更适合跨任务”作为前提，而应验证：**相同来源上，操作实例、抽象规则、实例＋必要前提，哪个在同分布和跨任务方向上更有用？**

两篇论文并不矛盾：一种比较“具体与抽象的内容形式”，另一种重点考察“旧抽象怎样影响持续更新”。适度的一次提炼可能便于迁移，与不应该反复摘要旧摘要可以同时成立；两个轴必须分开实验。

该文的 RR/NL 分组来自无记忆成功/失败题，但报告的变化还涉及跨任务记忆与仅学目标任务记忆的比较。其 FWT 不是简单的 REUSE−BASE。我们沿用清晰的损害/救回分解，不直接套 FWT 名字。

跨问题与跨任务也要区别：换一道 Hotpot 题只证明跨题；任务族或数据分布改变才开始涉及跨任务。首阶段可在 Hotpot 内预定义问题/操作族，之后做 A→B 和 B→A；类别仅用于离线分组，不把 gold 题型当运行特征。跨 Hotpot/2Wiki/MuSiQue 时还要区分任务变化、语料变化与底座变化，不能都归为记忆效果。

## 9. 两组实验应怎样设计得更干净

### 9.1 实验一：表示方式，不改变更新过程

固定原始来源记录、选中的来源 ID、当前问题和状态；比较：

- 具体查询操作记录，不抽象成通用规则。
- 从相同来源一次性提炼的短规则。
- 操作实例＋最少必要前提。

先固定候选 ID 检查表示内容，再固定表示比较选择器。若第一步就让每种写法各自召回不同来源，就无法判断差异来自内容还是检索。

比较自然长度和明确的等 token 预算两种条件，记录截断策略。不能把完整几十轮轨迹与几十字短卡的差异全说成“抽象的作用”；也不能为了等长而专门删掉具体记录的关键前提。

### 9.2 实验二：更新方式，不改变累计原始来源

| 对照 | 新内容如何产生 | 要回答什么 |
|---|---|---|
| 逐条保留，不整合 | 追加具体操作条目 | 不抽象是否已经足够 |
| 独立提炼，不看旧摘要 | 每批直接从本批原始记录提炼，正文不改旧卡 | 没有旧摘要影响是否更稳定；是否产生冗余 |
| 一次性抽象 | 某个检查点从截至当时的同一来源池一次生成 | 首次概括本身损失多少 |
| 持续改写 | 每次输入旧摘要与新增来源 | 递归内容依赖带来什么变化 |
| 从源重建 | 达到更新条件时，从截至当时的原始来源重新生成候选 | 能否保留有用抽象，又减少递归失真 |

“一次性抽象”是静态检查点参照，“从源重建”是触发、验收和替换的更新策略。若两者在相同检查点读取同一来源池、使用相同 prompt，它们就是同一个内容生成操作，不重复统计为两种独立算法；差异应放在何时重建、是否验收及怎样替换上。

每个检查点使用相同累计来源前缀，不能让“一次性”方法提前看完整未来数据。控制批次顺序、最终执行库容量、每题可见 token；另报生成/重建成本，并进行多种预先确定的顺序或随机种子。

若库规模大到原始来源放不下，重建使用预先固定的采样/选择规则，并让相应对照使用同一子集。不能一边无限回看原始数据、一边声称与只能保留固定预算旧记忆的方法完全同资源。

只改磁盘上的“覆盖/另存为”而生成输入完全相同，理论上不应改变模型行为。要测试漂移，操纵的是旧摘要是否可见、能否改正文、删除/保留权限，不是文件名。

## 10. 两套评价协议分开报告

### 10.1 独立适配—冻结评价：先做这个

官方 train 内来源/选择器/校准角色继续隔离；形成库后固定内容、范围、阈值和模型。正式目标阶段只读，结束时核对快照。测试 feedback、使用次数和 reliability 都不能写回到会影响后题的状态。

不因本轮讨论重新切官方数据。当前沿用 train 内约 80/10/10 的用途方案；现有小批量和已看过的 16 个校准题仍是开发数据，不变成新的盲测。

### 10.2 流式先预测—后更新：后做这个

```text
第 t 题到来 → 用 M_t 选择/执行 → 锁定预测与成本
          → 依协议收到反馈 → 形成 M_(t+1)
```

必须预先声明反馈是 gold、人工、judge 还是代理、何时到达、允许谁读，以及有没有额外离线配对。流水数据可来自允许学习的 train 流，不偷偷用官方隐藏测试标签做在线学习。

只运行 REUSE 时，线上通常看不到同题 FRESH 的反事实。单臂“答对了”不能直接形成精确 REUSE−FRESH 信用。选项是定期在允许学习的样本上执行额外配对（费用全计），或将单臂反馈记为较弱证据；后者不能和真实配对标签混合统计。

“先预测后更新”防止当前题标签提前泄漏，但不自动保证可与冻结测试成绩直接横比。两者分报告、分数据清单、分模型/记忆版本。

### 10.3 固定探针：不写回也可能成为调参集

保留固定题检验旧能力很重要，建议区分两种用途：

1. **开发探针：** 可以看结果、排错、按预定规则做开发决策；始终标为开发，不当最终测试。
2. **封闭评价探针：** 预先固定检查点，克隆记忆快照运行；结果不影响系统/研究者在该次实验中的阈值选择、选卡和提前停止，结束后统一分析。

探针的 query、检索轨迹、成功/失败、调用次数都不能写入执行记忆。即使不把答案存卡，只要反复根据探针成绩改算法，它也已参与开发。最终还需未用于设计的评价集。

固定探针应覆盖旧任务、易受误用的边界与原本可被 FRESH 修复的题，不只检查原本已正确的题。按固定步数检查，不在看到下降以后临时挑一个有利检查点。

在冻结协议中，探针可以用于建库期间预定的快照检查；最终测试库已经不再变化，无需为了“定期”重复付费跑同一套题。真正需要持续检查的是跨批次建库和后续流式更新阶段。

## 11. 如何防止“永远不用经验”看起来获胜

安全不能只看伤害率。以预先固定且完成的参照 X（BASE 或 FRESH）为例，分别记录：

```text
救回数 = X错误，待评策略正确
改坏数 = X正确，待评策略错误
净正确题变化 = 救回数 − 改坏数
```

同时报告救回率/改坏率（以完整预定义题集为分母），以及条件修复率/条件保留率（以 X 错题/X 对题为分母）。两套分母不能混。相应集合为空记 N/A；API 失败、未执行、弃答按预先协议另列，不事后移出分母。

| 必报内容 | 为什么需要 |
|---|---|
| 相对 BASE 的救回/改坏 | 整个流程是否破坏原有能力 |
| 相对 FRESH 的救回/改坏 | 记忆到底多救回或多损害多少 |
| 实际复用覆盖率 | 是有选择地复用，还是根本没有用 |
| 有卡覆盖与实际有效改写率 | 区分没有卡、拒绝卡、卡输出没改 query |
| 所有题的分数与已复用子集分数 | 避免只挑好题报效果 |
| 无增益、错误、弃答与未知 | 防止仅靠平均正确率掩盖问题 |
| 检索/模型调用、token、延迟、建库/验证成本 | 不能只展示线上少一次调用 |
| 固定旧题的跨检查点变化 | 检查新任务收益是否以旧能力为代价 |

若永不复用并使用同一份 FRESH 结果作为回退，**相对 FRESH** 的记忆救回、改坏和净增量都是零，覆盖率也为零；它可以相对 BASE 有修复收益，但那不是记忆功劳。若独立重跑 FRESH 出现模型波动，也不能归为记忆效果。若永不复用且使用同一份 BASE 回退，则相对 BASE 才是上述零变化。不能混淆两个退路。

比较方法建议：在相同实际覆盖水平或相同成本预算下比较救回—伤害关系；或者在校准集预设可接受伤害水平，评价能救回多少题。零覆盖是合法退路，不是研究成功；不应为了凑覆盖强迫明显不适用的经验上线。

如果充分实验后始终无法优于 FRESH，应接受记忆在当前设定下不必要，调整研究问题，而不是强行挑正例。

## 12. 对照与消融：保留用户清单，但明确它们的差异

| 对照 | 具体定义/注意事项 |
|---|---|
| BASE | 不修复的基础流程 |
| 固定多轮、无历史 | 预设多轮策略；若与 FRESH 修复策略相同，合并为同一对照，不重复命名 |
| FRESH 修复闭环 | 根据本题状态修复，无跨题经验；同预算的主要对照，可选明确的 Reflective/S2G 风格实现，但不冒称完整复现 |
| 具体经验复用 | 保存可核查查询操作片段，而不强制抽象；同来源、同长度协议 |
| 静态模式库＋上下文选择 | ReFormeR 等强近邻；固定来源量与反馈权限，否则动态法可能只是看了更多数据 |
| RRM 对齐路线 | 尽量对齐适用条件、query-only 使用、OQR 与维护；若不是原代码/同任务，只称明确的风格对照 |
| 去掉当前边界检查 | 只去掉待验证的软条件门，不取消来源隔离、gold 禁用和硬接口要求 |
| 去掉反例驱动调整 | 仍保存失败审计，但不让其影响选择或范围；区分没有记录与没有使用反馈 |
| 去掉改版重新验证 | 对照新版本直接继承旧资格与新版本回候选；只在隔离实验中运行 |
| 深度限制/从源重建 | 明确旧摘要可见性、内容派生链与成本；上限 1/2/3 属待测配置 |

“去掉版本控制”如果只是删 Git 或日志，不会有明确的算法效果解释。真正可测的是：新正文是否盲目继承可信资格、父卡是否被不可恢复地替换、是否能回到已验证执行配置。

## 13. 让创新问题具体到能被否定

“降低有害复用，同时保留有用修复”是目标，不是算法。建议先围绕一个可执行的机制组合测试：

> **操作正文冻结，反馈旁路追加；只在明确更新需求时提出新版本，优先回到原始来源；新版本在旧能力保留和独立新题增量两方面通过验证后才替换执行卡。**

最小可证伪假设：

- H1：固定来源与执行预算时，源记录直接生成的短卡能否比持续摘要改写取得更好的收益—伤害平衡？
- H2：替换前比较“旧卡/分别保留/FRESH”，能否比只看新版本自己成功率少丢失有用修复？
- H3：在同等覆盖或成本下，使用明确对照的反例事件能否提高选择，而不是仅让系统越来越保守？

其中 H1 的基本动机已被 Useful Memories 覆盖，H2/H3 又与 RRM、ReMe、QCR 及经验信用研究相邻。创新必须来自明确的更新/选择规则与优于近邻的证据，不来自“两层”“深度为2”“有反例”这些字段本身。

可先研究两个侧重点，而不扩大框架：

- **优先建议：经验持有与替换。** 当前卡是否值得留，新卡是否值得替换旧卡。短处是需要足够独立来源与验证题；优点是与“复用还是 FRESH”形成清楚的实验闭环。
- **配套研究：浅层表示稳定性。** 把内容写法和更新方式分开，检查信息在哪里丢掉。短处是与 Useful Memories 接近；价值在于为持有/替换规则提供具体机制证据，而不是单独重复其结论。

## 14. 下一次编码的最小顺序（本轮不实施）

1. **先补反馈语义：** 明确 comparator=BASE/FRESH、真实分支引用、独立题/来源角色、未知/失败/无增益，不能把旧 DIRECT 账本改名就复用。
2. **再补派生审计：** 真实内容输入、原始来源、父版本与计算深度；内容生成权限和执行资格分开。
3. **收紧执行视图：** 来源/hash 等管理元数据不整包进入改写 prompt；保留必要的当前绑定与程序性正文。
4. **只实现保留/暂停/从源生成候选：** 先不自动合并整库、不启用 EMA 晋升，也不同时加入文档层。
5. **最后接两个小型对照：** 同池表示实验、同来源更新实验；先冻结评价，流式后置。

测试重点：超过内容派生深度必须阻断；原始来源重建不可偷读旧摘要；新正文不能继承旧验证；探针和测试反馈不能改变执行库；unknown 不作 neutral；同题不同分支不算不同独立题。

这些是讨论后的建议，不是已运行的研究结果。具体上限、合并条件、风险阈值、探针数量及额外 API 预算仍需后续确认。
