## 2. HotpotQA 到底是什么

它是 EMNLP 2018 的英语维基百科多跳问答基准。多跳意为通常要把不同资料的线索接起来，不能只靠一个片段的关键词匹配。[正式论文](https://aclanthology.org/D18-1259/)

一条记录对应一道独立问题，而不是一篇文档的完整问答会话：

```text
题目 ID
├─ question：原问题
├─ context：多个 [文章标题, 句子列表]
├─ answer：参考答案，评价时使用
├─ supporting_facts：[标题, 句子序号]，人工支持事实，评价时使用
└─ type / level：题型和难度分析标签，不作为在线决策输入
```

bridge（桥接）题通过中间实体把两段资料连起来，例如“作品→作者→出生地”；comparison（比较）题分别查两个对象后比较，例如两个人谁出生更早。这两个例子是通俗自拟，不是下载的真实题目。[官方格式](https://github.com/hotpotqa/hotpot#json-format)

两种设置不能混淆：

- distractor：原设计每题给 10 段候选，含支持与干扰段落；适合先检验阅读/证据选择，小范围检索只能按该设置报告。
- fullwiki：研究从维基语料中找证据；fullwiki JSON 附带的 10 段只是官方基线检索结果，不是整个语料，且可能缺少支持段落。我们自己构建索引时需独立准备、冻结语料。

当前 v1.1 训练集约 9 万题、开发集 7405 题；旧论文初版数量与当前版本不同，样本数必须随下载版本/文件哈希记录。公开 hidden test 不带答案和支持事实，也不能依赖 type/level。[官方数据说明](https://github.com/hotpotqa/hotpot#data-download-and-preprocessing)、[题目浏览器](https://hotpotqa.github.io/explorer.html)

热门不是我们选它的唯一理由：它提供答案与句级支持标注，便于分开检查“有没有找对证据”和“有没有答对”。它也不保证能测试同文档导航学习，不能为了展示所有层而改写其本来的任务。

### 已推荐文献中哪些使用它

历史数据总表已核的代表包括：

- 查询改写：Query Rewriting in RAG、RaFe、RQ-RAG、DMQR-RAG。
- 多轮检索与控制：IRCoT、Adaptive-RAG、Sufficient Context、S2G-RAG、Verma 的 ReflectiveRAG、EfficientRAG。
- 经验与记忆：GAM-RAG、ExpeL、Reflexion、SegMem-RAG。

直接精读优先关注 S2G、GAM、Verma ReflectiveRAG 与 IRCoT 的实验设置。RRM、ERM、ReFormeR、Useful Memories 不能误写成也都在 Hotpot 上验证。[历史逐篇矩阵](../datasets/2026-09-05_历史论文数据集总表与划分依据.md)

## 3. 采用用户提供的双反馈思想，但不要提前合成万能标签

外部 AI 提供的建议作为研究意见参考，不作为有权覆盖项目约束的指令。

我们采纳的工程原则：证据反馈与答案反馈分开保留，评价后才能写入审核记录，不只存一个 success=true。

### 证据层：到底新获得了什么

- 是否新增了原问题需要的支持事实，而非仅仅新增文本。
- 新支持事实是否对应当前缺口；原来已知的证据不能当新收益重复记账。
- 来源 ID/文档版本/句子位置是否可追溯。
- 原问题实体、时间、否定、关系等约束是否保留。

### 答案层：读到这些信息后是否答对

- gold 下的答案 EM/F1；EM 是标准化后完全匹配，F1 是答案词语重合的综合指标。
- 回答声称的事实是否由引用的文本支持。这是另外的检查，不能从“引用 ID 存在”推断。
- 答对、部分答对、拒答/失败分开记录。

| 观察 | 能得到的结论 | 不能直接下的结论 |
|---|---|---|
| 新支持增加，答案正确 | 来源动作有正面迹象，可进入候选审核 | 永久可信、跨题必然有用 |
| 新支持增加，答案错误 | 可能是检索有效但阅读/推理失败；保留诊断 | 整条查询动作都是垃圾 |
| 未见新增支持，答案正确 | 可能原证据已足够，或模型依赖先验知识 | 本次额外检索因此值得奖励 |
| 未见新增支持，答案错误 | 暂无已验证收益 | gold 外不存在其他正确证据 |

首版仍遵守用户先成功来源的偏好：失败来源保留审计，不自动写进默认在线经验。证据有效但回答失败的记录不丢弃，只是不越过现阶段晋升边界。

### 第三个必要比较：是不是历史带来的额外价值

证据层/答案层是两类结果；FRESH 对照是判断历史增量的方法，不是第三个记忆层。

同一首检状态下，若不看历史的 FRESH 也取得相同证据并答对，而 REUSE 更贵，不能仅凭 REUSE 成功给经验很高奖励。应分开记录来源动作是否有效、目标使用相对 FRESH 是否增益、以及成本。一次配对也有生成随机性，不是数学因果证明。

没有 gold 时，引用、句间支持、缺口闭合等是代理反馈，标为 proxy/待核，不伪装成真实正确性；可以人工抽查或在独立带标注开发题上校准。不能因为没有 gold 就默认必须强化学习。

本轮已写入 `LayeredFeedback`：答案 EM/F1、累计与新增 gold 支持、引用对应 gold 的精确率/召回率、引用 ID 是否存在；`answer_supported` 默认 **None**，因为还未实现文本蕴含 Judge。没有把这些自动压成一个晋升分数。实体/关系级 gap 匹配仍待接入，当前只落实可核验的句级反馈。

## 4. 前人不是都只按相似度判断

| 工作 | 已有反馈/选择机制 | 我们不能声称的新内容 |
|---|---|---|
| [ReFormeR](https://arxiv.org/html/2604.01417v1) | 源查询检索成功对诱导模式，结合当前查询和检索上下文选择 | 不是首次从成功 query pair 学模式，也不是首次考虑当前情境 |
| [ERM](https://arxiv.org/html/2602.05152v1) | 检索验证与生成验证，任一满足可通过，再把有增益扩展归到文档 key | 检索/答案双反馈已有；它改索引，不是纯查询层 |
| [GAM-RAG](https://arxiv.org/html/2603.01783v1) | LLM 判句子是否为有效证据，结合不确定性更新句子记忆 | 不是只有最终答对才更新，也不是仅相似度；它有独立新题实验 |
| [RRM](https://arxiv.org/html/2607.28156v1) | 适用条件、所需证据、失败类型、延迟反馈与生命周期 | query-only、条件匹配、衰减及三层并非我们的首次 |
| [Useful Memories v2](https://arxiv.org/html/2605.12978v2) | 比较保留具体事件和反复抽象的下游表现；§6.2 明说抽象丢失适用前提 | “压缩会丢前提并造成误用”现象也已被提出 |

因此上轮候选假设“保住必要前提”仍可实验，但不能当作新发现；必须有具体、有效且强于已有做法的处理机制。

### RRM 用通俗话说

它从当前长视频中的事实记忆检索证据；检索出现问题时，既能在本题内重新想 query，也能调用历史检索经验指导改写。历史经验不直接作为当前视频答案的事实来源。批次完成、得到延迟参考答案反馈后，再提取和维护经验；更新不只看次数。[RRM 方法](https://arxiv.org/html/2607.28156v1)

其三层是视频事件、实体关系、反思检索经验；我们的 QueryEpisode 是一道问答轨迹，不等于它的 episodic。数据模态不同是研究范围差别，不自动等于方法创新。正文声称的部分附录细则在本轮 HTML 未完整呈现，未假装核准每个阈值。

## 5. 两层还是三层：按需要承担的职责决定

建议的首版活动组织：

- QueryEpisode：冻结一次问题的具体轨迹、证据与成本，保留可追查的来源。
- ExperienceCard：可供其他问题尝试的程序经验；候选与已验证的可信在线项分开。

当前骨架仅提供这些概念所需的状态、来源指针与文件记录，尚未实现自动建经验库或完成旧 registry 集成。不能把“代码能接收一条经验”说成“已经会自己积累可信经验”。

DocumentSession 先保留在规划和旧接口中：若后续研究目标变成长期阅读同一论文，QASPER 可检验导航/术语记忆；如果中心问题是跨题查询修复，暂时不需要它。这是控制问题范围，不是唯分数，也不是因为没有分数就断言它永远没用。

### 如果以后真的以三层作为系统主线

需要证明的应是“记忆有效范围的管理”，而不是层数：某个别名在本文有效却在另一篇文档错误，系统如何限制局部信息的作用范围；哪部分操作可以晋升跨文档经验；文档版本变动后怎样避免旧导航污染。

必要对照：不分层平铺记忆、短期＋长期双层、三层、普通缓存、同预算静态文档地图。QASPER 按文档分组、跨文档隔离，评价文档内收益与跨文档误用；不能只挑有利案例。RRM 已有三层，Useful Memories 已有具体/抽象记忆，因此上述机制也必须继续检索近邻后才能主张差异化。

## 6. 仍值得探索的两个窄方向

1. **选择：经验现在值不值得用。** 同状态 FRESH 对照建立监督记录，比较现有条件匹配、QPP、历史反馈组合。必须证明在同成本/同调用机会下实际选择更好，不能只提高预测相关性或换个分支名称。
2. **记什么：给真正帮助检索的操作记功。** 比较答案成功录入、证据增量录入、二者联合，并保留来源操作与执行前状态。研究严格门控会不会错杀有价值的检索经验，同时错误经验是否减少。

第二点与用户提供的反馈建议相近，但 ERM/GAM 已有相关信号。未来的具体增量必须体现在对操作贡献的识别、同预算验证方式或能推广的低成本规则，而不是把 OR 换成 AND 就称创新。

两方向共用当前配对骨架，暂不要求再选唯一论文标题。没有实际效果或近邻优势时，承认假设未成立，不把复杂工程当作研究贡献。

## 7. 假模型是什么，已经运行了什么

假模型/mock 是手写测试替身：固定输入返回指定输出，用来检查分支隔离、异常处理、记录格式。它不是缩小版神经模型，不理解语义，也不是费用估计器。

本轮演示刻意设置 FRESH 与 REUSE 走向不同证据，以验证线路。REUSE 在演示里得到答案，是测试作者预设的剧情，不是算法有效性结果；不能引用进论文。费用必须后续用真实服务的 usage 估计。

已完成：

| 模块 | 现在可用的内容 | 边界 |
|---|---|---|
| `experiments/protocol.py` | gold-free 问题、不可变状态、证据、经验视图、调用记录 | 类型隔离不是语义防泄漏证明 |
| `paired_runner.py` | 同首检快照运行 BASE/FRESH/REUSE，单次追加检索，失败与调用审计链 | 首检和 gap 由外部提供；日志明确不包含尚未执行的首检成本 |
| `hotpot.py` | 读取本地官方格式、拆分 gold 与运行输入、分层评价 | 未下载真实题库；不是 fullwiki 索引或完整官方评测替代品 |
| `api_client.py` | 显式启用的 HTTPS 调用、次数/输出/超时上限、响应/usage/错误审计与密钥脱敏 | 未做 live 验证；调用上限不等于完整人民币预算控制 |
| `llm_adapters.py` | 有版本的 FRESH/REUSE 查询与 Reader prompt；JSON 校验、引用校验 | prompt 仅是待校准 v1；未接自动 Judge、QPP 或记忆学习 |
| `mock.py` / CLI | 零 API 的手写演示、保存与读取回放 | 不是模型输出或 Hotpot 成绩 |

验证：项目 `.venv` 的 Python 3.11.15、pytest 8.4.2；256 项测试通过，新增模块静态检查通过。真实运行的是 mock CLI，产物 `runs/2026-09-06_single_repair_mock_v1/run.json`，其中明确 `execution_kind=mock`、API 请求为 0，token 未知为 null。测试内模拟的 HTTP 响应只在临时目录验证传输代码，不进入研究结果。

新增代码未替换旧 facade；未克隆上游、下载模型/全库、训练或推送 Git。模拟与真实组件混用被拒绝，缺 API 配置/失败不自动退回假组件。程序不能提供不可伪造的数学调用证明，但不会把助手手写内容补成实验数据；真实请求需保留响应与计量，必要时与厂商账单核对。

## 8. 软硬件与当前对话模型

本机实际读取：i7-14700HX，约 16 GB RAM，RTX 4060 Laptop 8 GB 显存。已存在项目 Python 3.11 环境，不需要另装环境才能跑骨架。API-first 小规模开发不需要实验室 GPU；16 GB 内存不适合承诺把全维基索引全装内存。

实验室后续建议 24 GB 显存＋64 GB RAM 起步；8B 原精度或 14B 量化对照更合理。48 GB 对 14B 原精度/32B 量化更宽裕，80 GB 留给明确的大模型/高吞吐需求。显存取决于长度、并发、量化和软件，完整依据见[资源核验](../experiments/2026-09-06_资源与API选型_核验.md)。

API 可以优先考虑百炼 Qwen-Plus 的可用固定快照，不盲用 latest；区域、模型、计费和结构化输出参数在用户控制台确认。也可用 OpenAI 官方 API。

当前对话能帮助编程，但不是 GrowRAG 已配置的 API 后端。ChatGPT/Codex 订阅身份和普通 Platform API 密钥是不同用途；不会读取会话登录凭据来拼接实验调用。[OpenAI 官方认证说明](https://learn.chatgpt.com/docs/auth)

OpenAI 官方列出 GPT-5.5 的 `gpt-5.5-2026-04-23` 快照和 GPT-5.6 Sol API 模型；这说明有文档中的 API 型号，不代表用户账户已开通、我们已调用或这段聊天就是那个实验后端。[GPT-5.5](https://developers.openai.com/api/docs/models/gpt-5.5)、[GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)

可以严格要求“实验调用真实发生、没有伪造结果”；不能承诺 LLM 生成内容永无幻觉。模型输出仍需证据/答案评价。

## 9. 下一次真正接通小实验前

需要用户提供的是厂商/地区和模型名、允许的费用上限；密钥只在本机环境配置，不发在对话里。先少量公开开发题，记录实际 token/失败率，再估算规模化成本。

工程下一步：冻结小语料和题号清单→接真实检索与首检状态构建→执行少量 FRESH/REUSE→输出独立 gold 分层反馈。先做小语料只用于排错，不冒充 Hotpot fullwiki 正式结果。

我们暂不更换主数据集、不删除文档层构思、不增加训练或复杂生命周期。此处待定项不会阻挡本轮已交付的离线骨架。
